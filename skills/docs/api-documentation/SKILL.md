# API 문서 작성

API의 호출 계약을 근거에 맞춰 설명한다. 일반 작성 지침에 더해, `eci-my247-api`에서 이상수가 반복 적용한 Swagger 문서 배치 관례를 조건부 참고 자료로 보존한다. 관례의 출처는 커밋과 현재 소스이며, 운영 환경이나 문서 생성 결과까지 검증한 기준은 아니다.

## 범위와 결과물

- 사용자가 지정한 API와 문서 산출물만 다룬다. 일부 엔드포인트 설명을 전체 시스템 문서화로 확대하지 않는다.
- 문서 위치·형식·독자·작성 언어가 지정되어 있으면 따른다. 별도 지정이 없으면 기존 문서 형식을 우선하고, 새 문서는 한글 Markdown을 기본으로 한다.
- OpenAPI 등 특정 형식이 요청되면 그 형식을 사용한다. Markdown을 추가 산출물로 강제하지 않는다.
- 문서 작성 중 구현 결함이나 불일치를 발견하면 근거와 함께 알린다. 구현 변경은 요청 범위에 포함된 경우에만 수행한다.

## Swagger 문서 배치 관례

도메인별 합성 Swagger 어노테이션과 `CommonResponse<T>` 문서용 응답 클래스를 사용하는 프로젝트이거나, 사용자가 그 방식을 적용하도록 요청한 경우에만 [Swagger 문서 분리 관례](references/swagger-documentation-conventions.md)를 읽는다. 도메인 안의 문서 배치, 공통 응답과 개별 응답의 분담, 실제 반환형과 문서 스키마의 대조 방법을 따른다.

이 방식을 사용하지 않는 프로젝트에 문서 작성만을 이유로 Controller 상속 구조, 공통 응답 포맷, 새 의존성을 도입하지 않는다. 기존 inline 어노테이션을 정리하는 작업도 요청된 범위에서만 수행한다.

## 근거 확인

1. 대상 API의 기존 문서와 사용자가 제공한 명세를 읽어 목적·범위·용어를 파악한다.
2. 현재 동작을 문서화한다면 라우트 또는 컨트롤러에서 요청·응답 모델, 관련 검증·인증·예외 처리까지 필요한 범위만 추적한다.
3. 설계 명세를 문서화한다면 제공된 명세를 기준으로 작성하고, 미구현 내용을 현재 동작으로 표현하지 않는다.
4. 소스와 명세가 다르면 사용자가 지정한 기준을 따른다. 기준이 없으면 차이와 근거를 남기고 어느 쪽이 실제 운영 동작인지 단정하지 않는다.

- 확인한 내용은 소스 경로·관련 심볼 또는 문서 위치로 추적할 수 있게 남긴다. 코드 줄 번호는 현재 파일에서 확인했을 때만 사용한다.
- 필드명이나 메서드명으로 추정한 의미는 확인된 계약과 구분한다. 근거가 없으면 `미확인`으로 표시하거나 해당 내용을 제외한다.
- 소스에서 확인한 동작, 제공된 명세, 실제 실행 결과를 구별한다. 정적 분석만으로 운영 환경의 동작을 검증했다고 쓰지 않는다.

## 계약별 확인 항목

대상 API에 해당하는 항목만 확인한다. 공통 설정의 영향을 받는 경우 해당 설정까지 확인한다.

| 항목 | 확인할 내용 |
| --- | --- |
| HTTP 계약 | 메서드, 실제 경로와 접두사, 요청·응답 콘텐츠 형식, 상태 코드 |
| 요청 | 경로·쿼리·헤더·본문 구분, 필드명, 자료형, 필수 여부, 기본값, 허용값 |
| 검증 | 검증 규칙과 실제 적용 위치, 누락·null·빈 값의 처리 차이, 확인 가능한 업무 제약 |
| 응답 | 직렬화되는 필드명과 자료형, 중첩 구조, null 가능성, 해당 시 목록·페이지 정보 |
| 인증·권한 | 인증 방식, 필요한 헤더·세션, 접근 권한과 적용 범위 |
| 오류 | 오류가 발생하는 조건, HTTP 상태 코드, 오류 코드와 응답 구조 |
| 상태 변경 | 생성·수정·삭제 등 실제 변경과 호출 결과에 영향을 주는 처리 |

- DTO 선언만으로 필수 여부나 실제 응답 포함 여부를 확정하지 않는다. 바인딩·검증·직렬화 설정과 사용 경로를 함께 확인한다.
- 인증·권한·오류 응답이 컨트롤러에 없더라도 공통 필터·미들웨어·예외 처리기의 영향을 확인한다. 찾지 못했다는 이유로 없다고 단정하지 않는다.
- 업무상 제약이나 오류 메시지를 임의로 추가하지 않는다. 프로젝트에 없는 응답 포맷·상태 코드·명명 규칙도 만들지 않는다.

## Markdown 기본 틀

기존 형식이 없을 때 필요한 부분만 선택해 사용한다. 빈 섹션과 해당하지 않는 표는 생략한다.

```markdown
# API 이름

목적과 사용 상황

## 호출 정보
HTTP 메서드와 경로, 필요한 인증·권한

## 요청
파라미터 위치, 필드, 자료형, 필수 여부, 제약

## 응답
상태 코드, 응답 필드, 오류 조건

## 예시
요청·응답 예시와 검증 여부

## 근거와 미확인 사항
참조한 소스·명세, 확인되지 않은 항목
```

## 예시와 완료 확인

- 예시는 확인한 필드와 제약에 맞춘 가상 값으로 작성한다. 토큰·개인정보 등 실제 민감한 값을 문서에 넣지 않는다.
- 직접 실행하지 않은 예시는 설명용임을 밝힌다. 실제 실행 결과를 사용하면 확인한 환경·조건과 검증 범위만 적는다.
- 문서 작성만을 위해 상태를 변경하는 API를 호출하지 않는다. 실행 검증이 요청되었다면 승인된 환경과 범위에서 수행한다.
- 문서의 메서드·경로·필드명·상태 코드가 근거와 일치하는지 확인하고, 기존 문서와 중복되거나 충돌하는 설명을 정리한다.
- 결과를 전달할 때 수정한 문서 위치와 확인 범위를 알린다. 남은 미확인 사항이 있으면 함께 적는다.
