# JavaDoc 작성

요청받은 Java 요소의 역할과 사용 계약을 소스에 맞게 한글 JavaDoc으로 설명한다. 대상 프로젝트의 문서 규약과 현재 구현을 먼저 확인하고, 타입·메서드·enum에 필요한 설명과 태그를 선택한다.

## 작업 범위

- 사용자가 지정한 파일·타입·메서드를 대상으로 한다. 단순 코드 수정 요청에 모든 클래스의 JavaDoc 작성을 추가하지 않는다.
- 별도 지정이 없으면 설명 문장은 한글로 쓰고 코드 식별자와 태그는 원래 표기를 유지한다.
- 주석 작성이 목적이면 메서드 서명이나 실행 로직을 변경하지 않는다. 설명과 구현이 다르면 확인된 차이를 알리고, 구현 변경은 요청 범위에 맞춰 판단한다.

## 작업 절차

1. 대상 소스와 인접한 JavaDoc, 프로젝트의 문서화 규칙을 확인한다.
2. 메서드 서명·구현·관련 호출부·테스트 중 설명에 필요한 근거를 읽는다. 선언만 보고 null 허용, 예외, 트랜잭션, 동시성 보장을 추측하지 않는다.
3. 유형별 주석을 작성할 때 [유형·레이어별 기준](references/type-and-layer-guidance.md)의 해당 절을 읽는다. Controller·Service 등 레이어가 관련될 때만 레이어별 절도 확인한다.
4. 첫 문장에 역할이나 결과를 요약한다. 이름을 되풀이하기보다 호출자가 알아야 할 전제·조건·부작용을 설명한다.
5. 아래 태그 기준을 적용하고 변경한 주석을 실제 코드와 다시 대조한다.

## 기본 주석 서식

- **JavaDoc은 설명이 짧아도 다중행으로 작성한다.** `/**`, 본문의 ` * ...`, 닫는 ` */`를 각각 별도 줄에 둔다. 클래스·메서드·필드·enum 상수와 `{@inheritDoc}`만 있는 주석에도 적용하며 `/** 설명 */`처럼 한 줄로 축약하지 않는다.
- **설명 본문과 첫 블록 태그 사이에는 빈 ` *` 줄을 정확히 한 줄 둔다.** `@param`, `@return`, `@throws` 등 태그 묶음 앞에 적용하고, 연속된 태그마다 빈 줄을 넣지는 않는다.

```java
/**
 * 업무 실패를 공통 오류 코드와 연결한다.
 */
```

## 본문과 태그 기준

- 코드만으로 자명한 getter/setter나 내부 처리의 줄별 설명을 늘리지 않는다. 단위·값의 의미·선행 조건처럼 사용에 영향을 주는 정보를 적는다.
- `@param`: **`@param 매개변수명 타입표기 내용`** 형식으로 작성한다. 매개변수명은 실제 선언과 일치시키고, 아래 매개변수 타입 표기 뒤에 값의 의미, 확인된 허용 범위나 null 처리 등을 설명한다.
- `@return`: 아래 반환 타입 표기로 시작한 뒤 반환값의 의미와 확인된 빈 값·null 조건을 설명한다. 생성자와 `void` 메서드에는 작성하지 않는다.
- `@throws`: 실제로 발생하고 호출자가 알아야 할 예외와 발생 조건을 설명한다. 발생할 수 있다는 추측만으로 예외 목록을 늘리지 않는다.
- 본문과 각 태그의 설명에서 클래스·메서드 등을 언급할 때는 아래 심볼 링크 기준을 적용한다.
- 재정의 메서드는 상위 계약과 달라지는 설명만 보완한다. 기존 규약에 맞으면 `{@inheritDoc}`을 사용할 수 있지만 원문 확인 없이 쓰지 않는다.
- `@author`, `@since`, `@version`은 프로젝트에서 요구하고 실제 값을 아는 경우에만 사용한다. 작성자나 버전을 만들지 않는다.

## 매개변수 타입 표기

- 기본 형식은 **`@param request {@link RequestDto} 내용`**이다. 생성자·메서드 인자와 record 구성요소를 설명하는 `@param`에 실제 선언 타입을 적는다. 매개변수명 자리는 그대로 두고, 그 뒤의 설명을 타입 표기로 시작한다.
- 타입 표기는 [반환 타입 표기](#반환-타입-표기)와 동일하다. 원시형은 `@param count {@code int} 내용`, 제네릭은 `@param ids {@link List}&lt;{@link AppPushHistEntityId}&gt; 내용`처럼 작성한다. 래퍼·중첩 제네릭·배열·타입 변수·와일드카드도 같은 기준을 적용하고, 타입 표기 뒤에는 공백 한 칸과 인자의 의미를 둔다.
- 타입 매개변수의 선언 태그는 **`@param <T> {@code T} 내용`**으로 작성한다. `T`를 실제 클래스처럼 링크하지 않고, 설명에 선언된 경계 타입을 언급하면 `{@link DtoClass}`로 연결한다. 구체적인 작성 예시는 [매개변수 타입 예시](references/type-and-layer-guidance.md#매개변수-타입-예시)를 읽는다.

## 반환 타입 표기

- 기본 형식은 **`@return {@link DtoClass} 내용`**이다. 메서드 시그니처의 실제 반환 타입을 사용하며, 클래스·인터페이스·enum·record는 `{@link Type}`으로 연결한다. 선언이 `List<DtoClass>`이면 내부에서 생성한 `ArrayList` 등 구현 클래스로 바꾸어 적지 않는다.
- 원시형은 **`@return {@code int} 내용`**처럼 `{@code ...}`로 표기한다. `Integer`, `Boolean` 같은 래퍼 클래스는 원시형이 아니므로 `{@link ...}`를 사용한다.
- 제네릭은 바깥 타입과 실제 타입 인수를 각각 링크한다. `List<AppPushHistEntityId>`의 소스 표기는 **`@return {@link List}&lt;{@link AppPushHistEntityId}&gt; 내용`**이다. 생성 문서에는 각 타입에 링크가 있는 `List<AppPushHistEntityId>`로 표시된다. 꺾쇠를 그대로 쓰면 JavaDoc에서 HTML로 해석할 수 있으므로 `&lt;`·`&gt;`로 이스케이프한다.
- 중첩 제네릭도 같은 규칙으로 표기하고 배열은 원소 타입 뒤에 `[]`를 붙인다. 구체 클래스가 아닌 타입 변수 `T`와 와일드카드 `?`는 `{@code T}`·`{@code ?}`로 표시하며, 경계 타입이 있으면 그 타입을 링크한다. 선언에 없는 구체 타입을 추측해 넣지 않는다.
- 타입 표기 뒤에는 공백 한 칸과 실제 반환 내용의 설명을 둔다. 타입명만 적고 의미 설명을 생략하지 않는다. 반환 타입별 예시가 필요하면 [반환 타입 예시](references/type-and-layer-guidance.md#반환-타입-예시)를 읽는다.

## 본문과 설명의 심볼 링크

- `@param`·`@return`뿐 아니라 요약·상세 본문, `@throws` 등의 설명에서도 **실제 클래스·인터페이스·enum·record·메서드·필드·상수를 언급하면 `{@link ...}`를 기본으로 적극 사용한다.** 단순 타입명을 일반 텍스트나 `{@code ...}`로 남기기보다 선언으로 이동할 수 있게 연결한다.
- 타입은 `{@link DtoClass}`, 메서드는 `{@link ServiceClass#find(Long)}`, 현재 타입의 메서드는 `{@link #find(Long)}`, 필드·enum 상수는 `{@link Type#FIELD}` 또는 `{@link #CONSTANT}` 형식으로 쓴다. 오버로드가 있으면 실제 인자 타입을 포함해 대상을 구분하고, 같은 이름의 타입이 있으면 완전 수식 이름으로 명확히 한다.
- 링크는 현재 소스·의존성에 존재하고 해석되는 선언을 대상으로 한다. 매개변수명·지역변수·원시형·타입 변수·리터럴·짧은 코드처럼 선언 링크 대상이 아닌 표현은 `{@code ...}`를 사용한다. 일반 업무 용어에 맞추려고 존재하지 않는 클래스를 만들거나 링크하지 않는다.
- 블록 태그의 고정 문법은 유지한다. `@param request`, `@param <T>`, `@throws IllegalArgumentException`, `@see Type#method()`의 대상 자리를 `{@link ...}`로 감싸지 않는다. 타입·메서드 언급을 추가로 연결할 때는 태그의 설명 부분에 링크를 넣는다. [본문·메서드 링크 예시](references/type-and-layer-guidance.md#본문과-메서드-링크-예시)를 참고한다.

## enum의 별도 문서화

- enum을 문서화할 때는 타입 JavaDoc의 한글 개념 설명과 `{@link #상수}` 목록, 각 상수의 한글 설명을 함께 두는 서식을 사용한다. 기존 프로젝트가 다른 서식을 정했다면 그 규약을 우선한다.
- 상수 이름만으로 알기 어려운 업무상 의미와 적용 조건을 적는다. 확인되지 않은 DB 저장값이나 상태 전이를 추가하지 않는다.
- 공개 API의 enum이며 API 문서화도 요청된 경우에는 기존 Swagger `@Schema`에 같은 의미를 병기한다. JavaDoc만 요청받았다면 Swagger 어노테이션이나 의존성을 추가·수정하지 않는다.
- 실제 작성 시 [enum 서식과 적용 조건](references/type-and-layer-guidance.md#enum-문서화-서식)를 읽는다. API 전체 명세도 함께 작업할 때만 `api-documentation`을 함께 적용한다.

## 결과물과 확인

- 파일 수정 요청이면 해당 소스의 JavaDoc을 수정한다. 예시 요청이면 복사할 수 있는 주석을 제공한다.
- 매개변수명·매개변수 타입·반환형·예외 조건·참조 링크가 실제 선언과 맞는지 확인한다. 본문과 태그 설명의 클래스·메서드 언급에도 링크 기준을 적용했는지, 오버로드와 링크 대상이 정확한지 확인한다. JavaDoc 안에서 HTML로 해석될 수 있는 코드는 `{@code ...}` 등으로 표시한다.
- 한 줄 JavaDoc이 남지 않았는지, 본문과 첫 블록 태그 사이의 빈 ` *` 줄이 있는지, `@param`·`@return`의 설명이 실제 선언 타입의 링크·코드 표기와 의미 설명으로 구성됐는지 확인한다. JavaDoc 생성 성공만으로 이 서식 검사까지 통과했다고 판단하지 않는다.
- 프로젝트에 JavaDoc 검사 절차가 있고 변경 범위상 필요하면 실행한다. 주석만 바꾼 작업에 관련 없는 전체 테스트를 일괄 실행하지 않는다.
- 결과 보고에는 변경한 대상과 확인 방법을 적는다. 문서 생성이나 실행 검증을 하지 않았다면 했다고 표현하지 않는다.
