# 스킬 유지보수와 공통 사용 안내

## 무엇을 고치면 되는가

| 바꾸려는 내용 | 수정할 파일 |
| --- | --- |
| 스킬의 이름·적용 조건·작업 절차 | 해당 스킬의 `SKILL.md` |
| 특정 상황에서만 필요한 상세 기준·예시 | 해당 스킬의 `references/` 문서 |
| 이투스 DB 명명·자료형·컬럼·인덱스 공통 규칙 | [database/etoos-postgresql-ddl/references/standards.md](database/etoos-postgresql-ddl/references/standards.md) |
| 이투스 가이드·용어사전 갱신 | [출처와 자료 관리 안내](database/etoos-postgresql-ddl/references/source-notes.md) |
| 카테고리의 분류 기준·상태 | `README.md`의 카테고리 표 |
| 목록에 표시할 카테고리·적용 작업·경로 | `README.md`의 스킬 목록 |
| 스킬 추가 방법 | 이 문서 |
| 설치·연결·저장소 위치 이전 | [SKILLS_SETUP.md](../SKILLS_SETUP.md) |

실제 작업 규칙은 해당 스킬 한 곳에서 관리한다. 목록에는 규칙을 복사하지 않고 선택에 필요한 요약만 둔다. `SKILL.md`의 적용 범위를 바꾸면 목록의 요약도 함께 맞춘다.

## 스킬 한 개의 구성

배치 경로는 `skills/<카테고리>/<스킬명>/SKILL.md`다. 각 스킬의 필수 파일은 `SKILL.md` 하나이며, 맨 위의 `---` 사이에는 YAML 형식의 식별 정보를 작성한다.

```yaml
---
name: java-javadoc
description: "Java 소스의 클래스·메서드 JavaDoc을 작성하거나 수정할 때 사용한다."
---
```

- `name`: 바로 위의 스킬 폴더명과 같게 쓴다. 카테고리명은 포함하지 않아도 되지만 전체 인벤토리에서 이름이 겹치지 않아야 한다. 영문 소문자·숫자·하이픈을 사용하며 64자 미만으로 짧게 정한다.
- `description`: **어떤 작업에서 선택할지**를 한글로 쓴다. 이름과 설명은 스킬 선택에 쓰이므로 핵심 작업을 앞에 둔다.
- 본문: 실제 수행 절차, 놓치기 쉬운 제약, 결과물과 확인 기준을 쓴다. 한글로 작성해도 된다.
- `references/`: 일부 작업에서만 필요한 상세 설명이 생길 때 추가한다. `SKILL.md`에 읽을 조건과 상대 링크를 적는다.
- `scripts/`, `assets/`, `agents/openai.yaml`: 실행 도구·결과물용 자산·표시 설정이 실제로 필요할 때만 추가한다. DB DDL 스킬에는 큰 용어사전을 부분 조회하는 스크립트가 있다.

## 카테고리 분류와 확장

카테고리는 한 단계만 두고, 그 아래에 **하나의 작업을 수행하는 스킬 폴더**를 둔다. 다음은 확장 시 경로 예시이며, 아직 존재하는 스킬을 뜻하지 않는다.

```text
skills/frontend/frontend-component-development/SKILL.md
skills/architecture/architecture-decision-record/SKILL.md
```

- 분류 기준은 [README.md](README.md)의 카테고리 표에서 관리한다. 라이브러리 이름이나 결과물의 확장자보다 스킬의 주목적을 기준으로 고른다.
- 예를 들어 DB 구조를 설계하는 스킬은 결과물이 Markdown이어도 `database`에 둔다. 이미 정해진 API를 설명하는 스킬은 구현 언어와 관계없이 `docs`에 둔다.
- 구조와 책임을 결정하는 작업은 `architecture`, 정해진 내용을 설명하는 작업은 `docs`에 둔다. 판단과 기록을 함께 하는 스킬은 주목적에 따라 한 곳에 둔다.
- 서버의 모델·입력 검증·예외 구현은 `backend`, 조회 저장소와 DB 저장 코드 매핑은 `database`에 둔다. 도메인 계층 구성 스킬에 각 분야의 세부 규칙을 복제하지 않는다.
- 여러 분야에 해당해도 스킬 파일을 복제하지 않는다. 대표 카테고리 한 곳에 두고 적용 조건에 관련 분야를 적는다.
- 현재 카테고리에 맞지 않는 반복 작업군이 생기면 새 카테고리를 추가한다. 비어 있는 분류를 미리 많이 만들 필요는 없다.
- 카테고리별 `README.md`는 현재 두지 않는다. 목록이 커져 전체 인벤토리만으로 선택하기 어려워질 때 도입하고, 그때는 루트에 카테고리 요약을, 각 카테고리에 스킬 목록을 두어 중복을 피한다.

## 새 스킬 추가

1. 반복할 작업 하나를 정한다. 예를 들어 광범위한 `architecture`보다 구체적인 `architecture-decision-record`가 적용 시점을 설명하기 쉽다.
2. 주목적에 맞는 카테고리를 고르고 `skills/<카테고리>/<스킬명>/` 폴더를 만든다. 필요한 카테고리가 없다면 함께 추가한다.
3. [_templates/SKILL.template.md](_templates/SKILL.template.md)를 새 폴더의 `SKILL.md`로 복사한다.
4. 이름·설명과 본문을 실제 지침으로 바꾸고, 작성 안내와 필요 없는 항목은 지운다. 빈 문서는 스킬 목록에 등록하지 않는다.
5. 상세 설명을 분리했다면 `SKILL.md`에 상대 링크와 읽을 조건을 추가한다. 원칙적으로 스킬 폴더 안에서 참조를 해결한다. 작업에 꼭 필요한 다른 스킬을 공유한다면 의존 관계와 함께 복사할 범위를 명시한다.
6. `README.md`의 카테고리 상태·스킬 목록·구조를 갱신한다. 진입 파일에는 실제 `카테고리/스킬명/SKILL.md` 경로를 연결한다. [설치 안내](../SKILLS_SETUP.md)에 따라 인벤토리 전체를 전역 경로에 연결한 경우 새 스킬이나 카테고리를 따로 등록할 필요는 없다.
7. 아래 확인 항목을 점검한 뒤 실제 요청 하나에 적용해 본다.

작성 중인 메모는 `_templates/` 등에 일반 `.md` 파일로 두고, 실행 지침을 갖추기 전에는 `SKILL.md`라는 이름을 쓰지 않는다. `_templates`라는 폴더명 자체가 자동 탐색을 막아주는 것은 아니다.

## 수정 후 확인

- 스킬 폴더명과 `name`이 일치하고, 다른 카테고리의 스킬을 포함해 이름이 겹치지 않는가?
- `name`, `description`과 본문이 채워졌고 미완성 작성 안내가 남지 않았는가?
- 설명만 보고 적용할 작업과 적용하지 않을 작업을 구별할 수 있는가?
- 링크된 파일이 존재하며, 필요한 상황에서만 읽도록 안내했는가?
- 사용자 요청이나 프로젝트의 기존 규칙을 불필요하게 덮어쓰지 않는가?
- 실제 요청으로 결과를 확인했는가? 형식 검사와 실제 작업 검증은 별개다.

선택 기준을 점검할 간단한 예시:

| 요청 | 기대하는 선택 |
| --- | --- |
| “이 Service 클래스의 JavaDoc을 작성해줘” | `java-javadoc` |
| “이 API의 요청·응답·오류를 문서로 정리해줘” | `api-documentation` |
| “이투스 기준으로 메뉴 관리 테이블을 설계해줘” | `etoos-db-modeling` → 최종 SQL 작성에 `etoos-postgresql-ddl` |
| “이 컬럼 명세를 이투스 규칙의 DDL 파일로 작성해줘” | `etoos-postgresql-ddl` |
| “새 도메인의 Controller·Service·Repository 구조를 잡아줘” | `java-domain-api-structure` |
| “이 Entity의 생성·수정 메서드와 응답 DTO를 작성해줘” | `java-model-conventions` |
| “요청값 검증과 예약 중복 오류를 구현해줘” | `java-api-validation-errors` |
| “이 QueryDSL 목록 조회를 기존 저장소 구성에 맞춰 추가해줘” | `querydsl-repository-conventions` |
| “DB의 A/B 코드를 의미 있는 enum으로 매핑해줘” | 직접 enum 매핑 가능 여부와 코드 의미 확인 후 `jpa-coded-enum-mapping` |
| “ACTIVE/INACTIVE가 그대로 저장되는 enum을 추가해줘” | Converter 스킬 적용 대상 아님; 기존 직접 매핑 유지 |
| “독립 SQL의 실행계획과 인덱스를 튜닝해줘” | 이 목록에서 전용 스킬 없음 |

## 커밋 이력에서 추출한 Java 관례 유지보수

2026-10-16 `eci-my247-api`의 `이상수 <sangsoo.lee@etoos.com>` 커밋을 근거로 Java 관련 스킬 5개를 추가하고 문서 스킬 2개를 보강했다. 비병합 478개 커밋의 메타데이터·변경 경로를 분류한 뒤 각 주제의 도입·수정·원복과 현재 `release@8b06115` 코드를 대조했다. 모든 diff의 모든 줄이나 운영 동작을 검증했다는 뜻은 아니다.

- 본문에는 반복 채택한 선택과 적용 조건을 두고, 대표 커밋·소스 경로·반례는 해당 스킬의 `references/`에 남긴다. 원본 저장소의 로컬 절대경로를 실행 의존성으로 만들지 않는다.
- 사용자 확정 조건, 반복 관찰한 관례, 초기 반입 코드, 다른 작성자의 원형을 보강한 경우를 구분한다. 새 증거가 있어도 단일 사례를 모든 도메인의 규칙으로 확대하지 않는다.
- Converter 조건은 사용자가 확정했다. 의미를 드러내지 않는 DB 업무 코드를 `ORDINAL`이나 `STRING`으로 그대로 표현할 수 없을 때 적용한다. 숫자라는 이유로 ordinal로 취급하거나, 저장값에 맞추려고 의미 없는 enum 상수명을 만들지 않는다.
- enum JavaDoc은 기존 `java-javadoc` 안에서 관리한다. API 문서까지 다루는 작업에만 Swagger 설명도 연결한다.
- 기술 사용법, 특정 업무 수치, 일회성 버그 대응은 기본적으로 추가하지 않는다. 원본에서 수정·삭제된 구현을 현재의 선호로 다시 저장하지 않는다.

## 이투스 DB 스킬 묶음 유지보수

- `etoos-db-modeling`은 설계 절차를, `etoos-postgresql-ddl`은 SQL 작성 절차와 공통 자료를 관리한다. 가이드가 모델링 결과도 `.sql`로 전달하도록 정하므로 설계 스킬은 DDL 스킬에 의존한다.
- 공통 기준은 `etoos-postgresql-ddl/references/standards.md` 한 곳에서 고친다. 보존 원문과 적용 기준을 구분하고 용어사전·예제 갱신은 출처 안내를 따른다.
- 설계 스킬을 배포할 때는 두 폴더를 같은 상위 디렉토리에 함께 복사하거나 연결한다. `etoos-db-modeling`만 복사하면 공통 규칙·사전·SQL 절차가 빠진다. DDL 스킬만 사용하는 경우에는 DDL 폴더만 옮겨도 된다.
- 용어 조회 도구는 Python 3 표준 라이브러리만 필요하다. 유지보수 중인 Python 3를 사용하며, 코드 문법은 3.6 이상을 요구한다. 자동으로 사전을 수정하지 않으며, 중복 후보와 원문 설명을 조회한다.
- `backdata`는 작업 완료 후 없어져도 된다. 스킬이 사용하는 가이드·사전·SQL은 이미 DDL 스킬에 보존되어 있으며, 자료 정리를 위해 원본을 자동 삭제하지 않는다.

## 다른 프로젝트에서 사용하는 방법

### 1. 작업 지시에서 경로를 알려주기

별도 설치 없이 현재 인벤토리를 참조하게 하는 방법이다. 아래 `<저장소를 내려받은 경로>`를 현재 환경의 실제 저장소 루트 경로로 바꾸고, 다음 문장 뒤에 실제 작업을 적는다.

```text
<저장소를 내려받은 경로>/skills/README.md를 스킬 인벤토리로 사용해줘.
목록에서 현재 작업에 맞는 스킬만 골라 해당 SKILL.md를 읽고 적용해줘.
```

같은 안내를 대상 프로젝트의 `AGENTS.md`에 추가해 반복 입력을 줄일 수도 있다. 기존 지침을 보존하면서 안내 문장만 추가한다. 해당 Codex 환경이 이 로컬 경로를 읽을 수 있어야 하며, 다른 컴퓨터나 원격 환경에서는 인벤토리를 복사하거나 경로를 바꿔야 한다. 전역 연결을 완료한 환경에서는 `~/.agents/skills/harness/README.md`를 안내할 수도 있다. `~`는 현재 사용자의 홈 디렉토리를 뜻한다.

### 2. 사용자 전역 스킬로 연결하기

[SKILLS_SETUP.md](../SKILLS_SETUP.md)의 운영체제별 절차에 따라 아래 연결을 설정한다. 심볼릭 링크는 원본 폴더를 복사하지 않고 그 위치를 가리키는 연결이다. 저장소를 내려받는 것만으로 연결이 생성되지는 않는다.

```text
~/.agents/skills/harness
  → <저장소를 내려받은 경로>/skills
```

- **적용 범위:** 연결을 설정한 컴퓨터의 같은 사용자 계정으로 실행하는 Codex의 여러 프로젝트. 다른 컴퓨터·원격 환경에는 이 연결이 전달되지 않는다.
- **추가·수정·삭제:** 원본 `skills/`만 관리한다. 새 카테고리와 스킬도 전체 연결 안에 포함되므로 스킬별 링크나 동기화 작업은 필요하지 않다.
- **탐색 대상:** 유효한 `SKILL.md`의 이름과 설명을 읽는다. `README.md`에 이름만 추가하거나 빈 폴더를 만드는 것으로 스킬이 등록되지는 않는다.
- **중복 방지:** 같은 스킬을 개별 링크·복사본으로 다시 등록하지 않는다. 다른 설치 스킬과 `name`이 겹치지 않는지도 확인한다.
- **상대 참조:** 전체 폴더 배치를 유지하므로 DB 설계 스킬과 DDL 스킬의 의존 관계도 보존된다.
- **반영 시점:** 새 채팅이나 스킬 목록에서 확인한다. 실행 중인 채팅에 나타나지 않으면 Codex를 다시 시작한다. 자동 탐색이 모든 작업에 해당 스킬을 무조건 적용한다는 뜻은 아니다.

**과거 검증 기록:** 2026-10-16 macOS에 설치된 Codex `0.162.0-alpha.17.2`의 스킬 탐색으로 다른 프로젝트와 임시 작업 폴더에서 당시 4개 스킬이 사용자 전역 범위로 활성화된 것을 확인했다. 새 카테고리에 임시 스킬을 추가한 뒤 별도 등록 없이 재탐색해 발견했고, 제거 후 목록에서도 사라지는 것을 확인했다. 임시 스킬은 제거했으며 실행 중인 모든 채팅의 즉시 갱신까지 검증한 것은 아니다. 다른 환경의 설치 결과는 해당 환경에서 확인한다.

### 3. 다른 컴퓨터에 연결하거나 원본 위치 바꾸기

프로젝트 루트의 [SKILLS_SETUP.md](../SKILLS_SETUP.md)에 설치·재연결 절차를 모아두었다. 다른 PC의 Codex에 이 문서를 읽고 설정하도록 요청하거나, 문서의 해당 운영체제 절차를 사용한다. 새 저장소 위치를 기준으로 연결한다.

원본 저장소 루트를 이동하면 전역 링크의 대상을 갱신한다. 원본 내부의 카테고리나 스킬만 이동했다면 전역 링크는 그대로 두고 목록·상대 참조를 갱신한다. PC 간 원본 파일의 동기화는 Git 등으로 별도 관리한다.

**공식 근거:** [스킬 구조·사용자 탐색 경로·심볼릭 링크 지원](https://learn.chatgpt.com/docs/build-skills), [스킬 목록과 새로고침](https://learn.chatgpt.com/docs/app-server#skills). 2026-10-16 확인. Codex의 탐색 방식이 바뀌면 이 안내도 갱신한다.
