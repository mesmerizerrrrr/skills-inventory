# Java 테스트 코드 작성

## 테스트 범위

**테스트 대상은 메소드 하나이며, 각 분기·시나리오는 별도의 `@Test` 메소드로 작성한다.** 일반 계층은 유닛 테스트로 격리하고, 실제 DB 연동은 Repository 계층의 쿼리 실행과 영속성 기능을 검증할 때만 허용한다.

| 대상 | 테스트 방식 |
| --- | --- |
| Service·Controller·도메인 객체·변환기·유틸리티 | 대상 객체를 직접 구성하고 메소드를 호출한다. Repository·외부 클라이언트 등 경계 의존성은 mock/stub으로 대체한다. Spring 컨텍스트나 실제 DB를 띄우지 않는다. |
| QueryDSL CustomRepository 구현·JPA Repository·JDBC DAO 등 Repository 역할의 구현 | 메소드가 수행하는 실제 쿼리·저장·조회·수정·삭제 결과를 H2 메모리 DB로 검증한다. 필요한 영속성 구성만 로드한다. |

Repository의 DB 연동 검증은 기술적으로 DB 통합 테스트이지만, 이 지침에서는 **Repository 계층에 한정한 명시적 예외**다. Service가 Repository를 호출한다는 이유로 Service 테스트까지 DB에 연결하지 않는다. Repository 내부의 DB와 무관한 계산·변환 메소드는 일반 유닛 테스트로 작성한다.

HTTP 요청부터 DB까지 연결하는 테스트, 전체 애플리케이션 컨텍스트를 띄우는 `@SpringBootTest`, E2E 검증을 이 작업에 추가하지 않는다. Controller도 메소드의 반환값·위임·예외를 검증하며, 이 결과로 HTTP 매핑·필터·직렬화까지 확인했다고 보고하지 않는다.

## 작성 전에 확인할 내용

1. 대상 메소드의 계약, 실제 구현, 의존성, 기존 테스트와 프로젝트 지침을 읽는다. 테스트 목적만으로 구현 코드를 변경하지 않는다.
2. 정상 처리, `if/else`, `switch`, 조기 반환, 예외 및 의미 있는 경계값을 정리한다. 복합 조건은 각 조건이 결과를 바꾸는 경우를 구분하고, 발생할 수 없는 분기를 억지로 만들지 않는다.
3. 각 시나리오의 입력·의존성 응답·기대 결과를 정하고, 별도 `@Test` 메소드에 대응시킨다. 현재 구현의 잘못된 동작을 그대로 기대값으로 고정하지 않는다.
4. 테스트 실행 JDK, Spring Boot/BOM, Gradle/Maven Wrapper, 기존 JUnit과 mock/assertion 도구를 확인한다.

## JUnit 버전과 의존성

- **적용 시점에 사용 가능한 최신 정식 JUnit 중 현재 프로젝트와 호환되는 버전을 사용한다.** 특정 major나 패치 버전을 이 스킬의 영구 기본값으로 고정하지 않는다. snapshot·milestone·RC는 기본 선택에서 제외한다.
- 공식 릴리스와 지원 JDK, 빌드 도구·테스트 실행기·Spring 테스트 지원의 호환성을 확인한다. 새 테스트에는 JUnit Jupiter의 `org.junit.jupiter.api.Test`와 `DisplayName`을 사용한다.
- Boot가 관리하는 버전도 확인하되, 관리된다는 이유만으로 최신이라고 간주하지 않는다. 더 최신인 호환 버전이 있으면 JUnit Platform·Jupiter·launcher의 정합성을 함께 맞춘다. 단일 API artifact만 올려 실행기와 버전을 어긋나게 하지 않는다.
- 호환성 제약으로 최신 릴리스를 쓸 수 없으면 사용 가능한 가장 최신 버전과 제약을 보고한다. 테스트 작성만을 위해 애플리케이션의 JDK·Boot나 운영 의존성을 일괄 업그레이드하지 않는다. 릴리스 확인이 불가능하면 최신 여부를 미확인으로 표시한다.
- 버전은 확인한 정확한 값으로 재현 가능하게 관리한다. `+`, `LATEST` 같은 동적 버전을 선언하지 않는다. 기존 BOM·version catalog·dependency management 방식을 존중한다.
- JUnit·Mockito 등의 의존성은 테스트 범위에 둔다. H2가 필요한 Repository 테스트에는 `com.h2database:h2`를 테스트 범위로 추가한다. H2는 Spring Boot가 자동 구성할 수 있는 DB이며, 모든 Spring 프로젝트에 라이브러리가 기본 포함되는 것은 아니다.
- `build.gradle(.kts)`·`pom.xml`·version catalog의 변경은 필요한 **테스트 의존성·테스트 실행기 설정**에 한정한다. 이는 아래의 테스트 환경설정 위치 규칙과 구분하며, DB URL·profile·테스트 Bean을 빌드 파일로 옮기지 않는다.

버전 판단에 필요한 규칙은 위에 포함되어 있다. 최신 릴리스 확인에는 [JUnit 공식 문서](https://docs.junit.org/current/overview.html)와 [릴리스 노트](https://docs.junit.org/current/release-notes/index.html)를 참고한다.

## 메소드·분기별 테스트 작성

- 하나의 테스트는 하나의 대상 메소드와 하나의 분기·시나리오를 검증한다. 정상·실패·빈 결과 등을 한 테스트에서 순서대로 실행하지 않는다.
- 분기마다 독립적인 `@Test` 메소드와 한글 `@DisplayName`을 붙인다. 메소드명은 `sendMessage`, `sendMessage_whenRecipientMissing`처럼 대상과 조건을 구별할 수 있게 쓴다. 표시 이름에는 조건과 기대 동작을 드러낸다.
- 서로 다른 분기를 반복문·조건문·`@ParameterizedTest`·동적 테스트 하나로 합치지 않는다. 같은 분기의 입력 변형도 기본적으로 개별 `@Test`로 작성한다.
- 대상 메소드는 `when`에서 한 번 호출하는 것을 기본으로 한다. 준비용 fixture 생성·Repository 데이터 저장과 검증용 재조회는 대상 동작 호출과 구분한다.
- 같은 결과를 설명하는 여러 assertion은 한 테스트 안에 둘 수 있다. “테스트 하나당 assertion 하나”를 강제하지 않는다. 서로 다른 시나리오를 묶는 데 `assertAll`을 사용하지 않는다.
- 대상 객체 자체나 검증하려는 메소드를 mock하지 않는다. 반환값·상태·예외·중요한 외부 위임을 검증하고, 구현 세부 호출 순서를 불필요하게 고정하지 않는다.
- private 메소드만 호출하려고 reflection을 사용하거나 접근제어자를 바꾸지 않는다. 기존 공개 진입점에서 해당 분기를 검증한다.

## given / when / then 형식

**모든 `@Test` 메소드에 다음 주석을 정확히 표기하고, 각 영역 시작점에 둔다.** 짧은 테스트에도 생략하지 않으며, 일반 구현의 한글 구간 주석 규칙으로 대체하지 않는다. 메소드의 여는 중괄호 다음에는 예시처럼 빈 줄을 둔다.

```java
@Test
@DisplayName("메시지 발송 처리 테스트")
void sendMessage() {

    // given

    // when

    // then

}
```

- `// given`: 입력과 fixture, mock/stub 응답, 테스트 사전 상태를 준비한다.
- `// when`: 대상 메소드를 실행하고 결과를 받는다.
- `// then`: 반환값·상태·예외·필수 상호작용을 검증한다. 출력만 하고 끝내거나 assertion 없는 테스트를 만들지 않는다.
- 예외 테스트도 세 영역을 유지한다. 예외를 `when`에서 포착하고 `then`에서 타입·업무 오류 정보를 검증한다. assertion API가 호출을 감싸는 방식이면 실행과 포착을 `when`에 두되 실제 실행은 한 번만 한다.

분기별 테스트와 예외 포착·fixture 작성 예시가 필요하면 [테스트와 fixture 예시](references/test-examples.md)를 읽는다.

## fixture 공통화

- 여러 테스트에서 재사용하는 객체 생성은 `MessageFixture`, `OrderFixture`처럼 **도메인·기능별 별도 클래스**로 모은다. `src/test/java` 아래 해당 기능의 `fixture` 패키지 등에 두고, 전 프로젝트의 모든 데이터를 한 `TestFixture`에 몰아넣지 않는다.
- fixture는 필요한 기본값과 의미 있는 변형을 제공한다. 각 테스트의 분기를 결정하는 값은 메소드명이나 인자로 드러내고, 수십 개 플래그를 받는 범용 생성기를 만들지 않는다.
- 호출할 때마다 새 객체·가변 컬렉션을 반환한다. 수정 가능한 `static` 객체를 공유하거나 다른 테스트가 만든 상태에 의존하지 않는다. 시간·난수 값도 기대 결과를 바꾸지 않도록 고정 입력으로 제어한다.
- `@BeforeEach`에는 모든 테스트가 실제로 공유하는 대상 객체·mock 초기화만 둔다. 분기별 stubbing과 기대값은 각 테스트의 `given`·`then`에서 읽을 수 있게 남긴다.
- 데이터 생성의 공통화와 테스트 실행·검증의 공통화를 혼동하지 않는다. fixture 메소드 안에서 대상 업무 메소드를 실행하거나 assertion을 감추지 않는다.

## 테스트 전용 코드·환경의 위치

| 내용 | 위치 |
| --- | --- |
| 테스트 클래스, fixture, stub, 테스트 전용 설정 클래스 | `src/test/java` 또는 프로젝트에 이미 지정된 test 소스 디렉토리 |
| H2 연결·JPA 설정, 테스트 profile, SQL·입력 파일 | `src/test/resources` 또는 해당 test 리소스 디렉토리 |
| 테스트용 라이브러리와 테스트 실행기 연결 | 빌드 파일의 테스트 범위 설정만 |

**테스트 환경은 test 디렉토리 아래의 설정으로 제어하며, 테스트를 위해 실제 구현 디렉토리를 추가·수정하지 않는다.** `src/main/java`, `src/main/resources`에 테스트용 Bean·profile·H2 설정·DDL·데이터를 넣지 않는다. 테스트 전용 생성자·setter·접근제어자 변경·조건 분기를 운영 코드에 추가하지 않는다.

테스트에서 필요한 최소 설정은 test 경로의 설정 클래스로 제공한다. 구현 결함이나 구조 때문에 이 범위에서 테스트할 수 없으면 원인과 필요한 변경을 별도로 보고한다. 테스트를 통과시키기 위한 구현 수정이나 관련 없는 리팩터링을 섞지 않는다.

## Repository의 DB 연동

- 별도 지시가 없으면 **H2 메모리 DB**를 사용한다. 일반 유닛 테스트에는 H2나 Spring 컨텍스트를 추가하지 않는다.
- QueryDSL 구현의 실제 쿼리 결과와 JPA Repository의 필요한 저장·조회·수정·삭제 동작을 검증한다. 쿼리를 mock한 결과를 실제 SQL 검증이라고 보고하지 않는다.
- `@DataJpaTest`, `@JdbcTest` 등 프로젝트 버전에 맞는 최소 테스트 구성을 선택한다. QueryDSL factory·커스텀 Repository에 필요한 Bean은 test 경로에서 연결한다. Service·Controller·외부 연동까지 로드하지 않는다.
- 테스트 profile, H2 연결, 스키마·데이터 준비와 초기화는 test 경로 안에서 해결한다. 환경변수나 운영 기본 설정이 적용되어 실제 DB로 연결되지 않는지 확인한다.
- 실제 조회·영속성 검증 시에는 fixture 저장 후 필요한 `flush`·`clear`, 트랜잭션 롤백 또는 명시적 초기화로 1차 캐시와 테스트 간 데이터 간섭을 제거한다. 조회 테스트의 `given`에서 fixture를 저장할 수 있지만, `when`의 대상 조회에 불필요한 쓰기 동작을 섞지 않는다.
- H2가 지원하지 않는 운영 DB 전용 문법·함수를 만나면 SQL 의미를 바꾸거나 운영 코드를 고쳐 통과시키지 않는다. H2에서 검증 가능한 부분과 남은 호환성 한계를 보고하고, 별도 DB 사용은 사용자의 지시에 따른다.

Repository 테스트를 작성할 때는 [H2와 Repository 테스트 설정](references/repository-tests.md)을 읽는다.

## 완료 확인

- 요청한 메소드의 각 의미 있는 분기·예외가 별도 `@Test`에 대응하고, 한글 `@DisplayName`과 세 영역 주석이 있는지 확인한다.
- 일반 계층의 DB·외부 시스템 의존성이 격리되고, 실제 DB 연동은 Repository 테스트에만 있는지 확인한다.
- fixture의 재사용 범위와 상태 격리를 확인하고, 환경설정·테스트 코드가 test 경로에만 있는지 diff로 확인한다. 기존에 사용자가 변경한 구현 파일과 이번 작업의 변경을 구분한다.
- 프로젝트 Wrapper로 변경한 테스트부터 실행한다. 예: `./gradlew test --tests '패키지.대상Test'`, `./mvnw -Dtest=대상Test test`. 멀티모듈이면 해당 모듈을 지정한다. 의존성·실행기 설정을 변경했으면 영향받는 테스트 실행도 확인한다.
- 결과에는 작성한 테스트·분기, 선택한 JUnit 버전과 호환성 제약, 실행 명령·성공/실패·미실행 사유를 적는다. H2 실행 성공만으로 운영 DB의 SQL 호환성까지 검증했다고 보고하지 않는다.
