# Java API 검증·예외 작성

`eci-my247-api`에서 이상수가 반복해 구현·보강한 검증과 오류 표현 방식을 기본값으로 삼는다. 대상 프로젝트의 기존 예외 계층·응답 계약과 사용자의 명시적 선택을 우선한다.

## 적용할 코드 확인

요청 DTO, 해당 Controller, 호출 Service, 공통 예외 처리기를 이어서 읽는다. 같은 프로젝트의 `BaseException`, `ResponseCode`, `NotFoundException`에 해당하는 타입을 재사용한다. 다른 구조의 프로젝트에 이 이름의 공통 프레임워크를 새로 도입하는 작업으로 확대하지 않는다.

## 요청 검증의 배치

| 검증 종류 | 선호하는 위치와 표현 |
| --- | --- |
| 입력 자체의 필수값·길이·범위 | 요청 DTO의 제약 어노테이션에 사용자가 이해할 한글 `message`를 함께 적는다. 이미 `@Schema`가 있으면 해당 제약 설명도 맞춘다. |
| 요청 필드끼리의 조건 | 간단한 조건은 요청 DTO의 `is...Valid()` 형태 메서드에 `@AssertTrue(message = "...")`를 붙이고, Swagger를 사용하는 코드에서는 `@Hidden`으로 내부 검증 메서드를 숨긴다. |
| 조회한 데이터·사용자·업무 상태가 필요한 판단 | Service 등 기존 업무 판단 위치에서 검사하고, 해당 도메인의 의미가 드러나는 예외를 발생시킨다. 요청 DTO에 Repository를 주입하지 않는다. |

- 복합 검증의 누락값 처리는 필드의 필수 검증과 맞춘다. 선택값을 새로 필수값으로 만들거나, 다른 필드의 누락 때문에 검증 메서드에서 NPE가 나도록 하지 않는다.
- 기존 App/Internal 진입점이 같은 요청 모델을 받으면 양쪽의 검증 적용 여부를 확인한다. `@Schema`나 `@Hidden`을 런타임 검증으로 간주하지 않는다.
- 파일 형식·크기처럼 공통 검증기가 이미 분리되어 있으면 기존 `commons/presentation/validation`의 어노테이션과 `validator` 구현을 재사용한다. 한 번만 쓰는 작은 조건을 위해 별도 검증 체계를 만들 필요는 없다.

## 업무 예외와 응답 연결

1. 새 실패 조건이 기존 응답 코드의 의미에 포함되는지 먼저 확인한다. 단순히 메시지가 다르다는 이유로 새 오류 코드를 만들지 않는다.
2. 클라이언트가 구분해야 하는 업무 실패는 같은 의미의 기존 예외를 우선 재사용한다. 새 타입이 필요할 때 도메인의 `application/exception(s)`에 의미 있는 예외를 두고, 기존 `BaseException`과 `ResponseCode`에 연결한다. 새 코드가 필요하면 대상 프로젝트의 코드 배정과 HTTP 상태 규칙을 따른다.
3. 조회 대상 미존재는 기존 도메인 `...NotFoundException` 또는 공통 `NotFoundException` 체계를 사용한다. 같은 의미의 오류 계층을 중복 생성하지 않는다.
4. 하나의 업무 코드 안에서 이유를 설명해야 하면 공통 예외의 상세 메시지 생성자를 사용한다. 예외를 잡아 Controller마다 오류 JSON을 조립하는 방식은 추가하지 않는다.

공통 Advice가 성공 응답을 감싸는 프로젝트에서는 기존처럼 실제 DTO·목록·`void`를 반환한다. 예외는 공통 처리기가 응답 코드·메시지·HTTP 상태로 변환하도록 연결한다. 적용 중인 Advice 범위를 확인하고 동일 응답을 중복 포장하지 않는다.

## 결과 확인

변경한 실패 조건이 어떤 예외·응답 코드로 이어지는지, 상세 메시지가 실제 공통 처리기를 통과하는지 확인한다. DTO 검증을 바꾸었으면 해당 진입점에서 실행되는지도 확인한다. 새로 정의한 오류 계약에 필요한 범위의 기존 테스트 또는 호출 검증을 사용하며, 구현과 문서의 상태 코드·메시지가 일치하는지 대조한다.

세부 관례의 출처를 확인하거나 기존 코드가 서로 다를 때만 [근거와 적용 경계](references/conventions-and-evidence.md)를 읽는다.
