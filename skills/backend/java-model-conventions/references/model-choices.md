# 모델 선택과 표기

## Entity 생성·변경

- 생성 의도와 필요한 입력이 드러나는 정적 메서드를 사용한다. 이미 `ofCreateRequest(request, relatedEntity)`를 쓰는 도메인은 그 방식을, `create(field, ...)`를 쓰는 도메인은 그 방식을 이어 쓴다. 하나의 이름이나 입력 형태로 통일하지 않는다.
- 상태 변경은 Entity 안의 의미 있는 메서드로 표현한다. 설문 참여 모델이라면 `ofSurveyStart`, `sectionSubmitted`, `complete`처럼 단계별 의도를 드러낼 수 있다. 메서드 이름의 예시를 이유로 다른 업무에 설문 규칙이나 시간 정책을 추가하지 않는다.
- 요청 DTO를 Entity가 직접 받는 기존 구조도 허용한다. 별도 command 모델을 의무적으로 만들거나 DTO 의존을 제거하는 리팩터링으로 확대하지 않는다.
- 이미 setter가 필요한 관계 필드나 조립 모델은 그 이유를 확인하고 유지한다. 특정 관계 목록에 개별 `@Setter`가 필요한 경우와 모든 필드를 임의로 변경할 수 있게 하는 경우를 구분한다.

## 응답 변환과 record/class

| 상황 | 이 관례에서의 기본 선택 |
| --- | --- |
| 한 번 구성해 반환하는 단순 응답, 이벤트 값 묶음 | record와 생성자 또는 명명된 정적 팩토리 |
| Entity와 준비된 연관 자료를 응답으로 변환 | 응답 DTO의 `ofEntity`·`of...` 또는 생성자. 서비스가 조회한 자료를 인자로 전달 |
| 요청 바인딩 후 경로·인증 주체를 보충하는 모델 | 기존 mutable class와 필요한 setter 유지 |
| 상속 기반 공통 요청, 단계별 집계나 응답 조립 | 기존 class 구조 유지. record로 바꾸기 위해 호출 흐름을 재설계하지 않음 |

DTO 안에서 응답 표현을 만드는 것과 DB 조회·외부 호출을 수행하는 것을 구별한다. 메뉴 트리 응답을 예로 들면 서비스가 조회·정렬·부모별 그룹화를 하고 DTO가 전달받은 자료를 응답 트리로 변환한다. 단순 변환을 위해 DTO마다 별도 Mapper 계층을 만들 필요는 없다.

필드 이름·접근자·생성자 변경이 직렬화 계약을 바꿀 수 있으므로 기존 JSON 이름을 따라간다. boolean 필드의 이름만으로 직렬화 결과를 단정하거나 특정 접두사를 일괄 금지하지 않는다.

## 정확한 null 표기와 final

- 모델의 null 계약에 JSpecify를 사용하는 프로젝트에서는 `org.jspecify.annotations.NonNull`과 `org.jspecify.annotations.Nullable`의 정확한 import를 유지한다. 코드에 `@NonNull`이 있다는 이유만으로 런타임 null 검사를 구현했다고 간주하지 않는다.
- 입력 제약의 `jakarta.validation.constraints.NotNull`은 별개다. 모델의 null 계약 표기를 Bean Validation 대용으로 쓰거나, 검증 어노테이션을 JSpecify로 교체하지 않는다. 프로젝트가 다른 null 표기 체계를 쓰면 기존 체계를 따른다.
- 구현 메서드에서 재할당하지 않는 매개변수는 `final`을 우선한다. 인터페이스 선언까지 기계적으로 추가하거나 의도적으로 재할당하는 지역변수를 억지로 분리하지 않는다.
- 포함된 IDE 설정은 지역변수 `final` 생성을 선호하지만 모든 기존 변수에 강제할 규칙은 아니다. 새 코드의 인접 표현에 맞추고, 스타일 변경만으로 넓은 diff를 만들지 않는다.

## 기본으로 넣지 않는 요소

`@Builder`, `@Data`, 모든 필드의 setter, 별도 Mapper, 커스텀 null 처리 추상화를 편의상 일괄 추가하지 않는다. 필요성과 해당 도메인의 기존 사용을 보고 선택한다. 이 제한은 해당 요소의 사용 금지를 의미하지 않는다.
