# 조회 결과 형태 선택

DTO 직접 조회와 중간 Row·VO 중 선택하거나 기존 조회를 분리할 때만 읽는다. 아래 예시는 결과의 용도와 책임을 설명하며, 실제 클래스명과 패키지 위치는 대상 도메인의 구조에 맞춘다.

## 용도에 따른 결과 형태

| 결과의 용도 | 선택할 형태와 책임 | 가상 예시 |
| --- | --- | --- |
| 필요한 컬럼이 바로 최종 응답이 됨 | 기존 응답 DTO의 projection 생성자로 조회. record와 class 중 기존 형태를 유지 | `ItemSummary(id, title)`의 `@QueryProjection` 생성자를 `QItemSummary`로 호출 |
| 조회 인수에 순수한 값 변환만 필요함 | DTO 생성자·팩토리에서 변환하고 조인·DB 조회는 Repository에서 처리 | 원본 URL과 파일 URL을 받아 응답 URL 하나를 선택 |
| 후속 조회나 여러 결과 조립이 필요함 | Row·VO로 조회하고 Service 등 기존 조립 계층에서 응답 생성 | `OrderRow` 목록과 주문 ID별 `List<LineRow>` Map을 결합 |
| 엔티티 자체가 후속 처리에 필요함 | 기존 엔티티 조회 계약을 유지하고 필요한 시점에 DTO로 변환 | 분류 엔티티 목록으로 부모·자식 응답 트리를 구성 |

- 중간 객체를 `application/vo` 또는 `infrastructure/vo`에 둘지는 인접 구현에 맞춘다. 예시를 위해 새로운 공통 Row 계층을 만들지 않는다.
- 부모 목록과 하위 목록을 나누어 조회한다면 실제 부모 ID 목록을 기준으로 관련 데이터를 읽고 `Map<ID, List<...>>`로 조립하는 방식을 검토한다. 단순 조회에 불필요한 후속 조회를 추가하지 않는다.
- 조립 단계에서 부모 순서, 하위 목록 순서, 중복·빈 목록 처리가 기존 계약과 일치하는지 확인한다.

## 함께 확인할 선택

- `PageImpl`과 `PageableExecutionUtils`는 서로 다른 조회에서 공존할 수 있다. 메모리 필터나 slice를 포함한 특정 구현을 표준 페이징 기법으로 삼지 않는다.
- `Projections.constructor`와 `@QueryProjection`의 선택은 주변 코드와 변경 목적에 맞춘다. 생성자 인수의 순서·타입과 실제 응답 형태를 함께 확인한다.
- 트랜잭션 경계는 호출 흐름과 데이터 접근 계약에 맞춘다. Service를 새로 만들거나 트랜잭션을 조정하면 [Service 트랜잭션과 readOnly](../../../architecture/java-domain-api-structure/SKILL.md#service-트랜잭션과-readonly)의 조회·쓰기 및 DB 분기 기준을 따른다. 조회 성능 개선만을 이유로 읽기 전용 설정을 제거하거나 기존 트랜잭션 경계를 일괄 변경하지 않는다.
- 공통 지원 클래스에 `fetchPage`나 `hasAnyBit` 같은 도구가 있더라도 해당 조회에 필요한 경우에만 사용한다.
- 조회 형태를 선택했다는 사실만으로 운영 성능이나 데이터 정확성이 보장되지는 않는다. 변경한 조립·정렬·페이징의 결과를 필요한 범위에서 검증한다.
