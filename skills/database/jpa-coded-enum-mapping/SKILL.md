# JPA 업무 코드 enum 매핑

## 목적과 적용 조건

DB의 실제 업무 코드는 보존하고 Java에서는 의미를 읽을 수 있는 enum 상수명을 사용한다. **값이 사람이 이해하는 단어가 아닌 불투명한 업무 코드이며, `@Enumerated(EnumType.ORDINAL)` 또는 `STRING`으로 업무 의미와 저장값을 그대로 표현할 수 없는 경우**에 Converter를 적용한다.

- 숫자 컬럼이라는 사실만으로 enum이나 Converter를 만들지 않는다. 수량·식별자·비트마스크와 단일 업무 코드를 먼저 구분한다.
- `ORDINAL`은 enum의 선언 순서에 따른 값이다. 임의의 숫자 업무 코드로 간주하지 않는다. 선언 순서를 억지로 바꾸거나 의미 없는 상수를 끼워 넣어 업무 코드에 맞추지 않는다.
- enum 상수명을 `A` 같은 코드로 바꾸어 `STRING`에 맞추지 않는다. 반대로 의미 있는 enum명과 DB 값이 이미 같다면 기존 `STRING` 매핑을 유지한다.

## 작업 절차

1. **코드와 의미를 먼저 확인**
   - 컬럼의 실제 타입과 저장 표현, 코드별 업무 의미를 명세·기존 저장 코드·조회 코드에서 확인한다. 숫자의 순서나 문자 모양으로 의미를 추측하지 않는다.
   - 대상 Entity 필드, enum, 기존 Converter와 사용처를 함께 읽는다. null·미정의 값의 현재 처리와 같은 enum을 사용하는 다른 컬럼의 코드 체계도 확인한다.
   - 적용 조건이 맞는지 또는 공통 Converter 적용 범위가 애매할 때는 [코드 매핑 적용 판단](references/mapping-decisions.md)을 읽는다.

2. **의미명과 DB 값을 분리**
   - enum은 업무 의미를 나타내는 이름을 사용하고, 실제 저장 코드는 별도 값으로 보유한다. DB 컬럼 타입과 문자열 앞자리 0 같은 저장 표현을 그대로 맞춘다.
   - 프로젝트에 `PersistableCodeEnum<T>`와 `DatabaseCodeConverter<E, T>`가 있다면 이를 재사용한다. 도메인 enum은 인터페이스를 구현하고, `infrastructure/converter/<Enum>Converter`가 기존 공통 Converter를 연결하는 구성을 선호한다.
   - 같은 공통 구조가 없는 프로젝트에서는 해당 코드 매핑에 필요한 최소 구현을 선택한다. 이 스킬 때문에 두 추상화를 포함한 공통 체계를 대규모로 도입하지 않는다.

3. **적용 범위와 기존 계약 유지**
   - `autoApply`는 패키지 경계가 아니라 대상 Java 타입의 다른 필드에도 영향을 준다. 같은 타입의 저장 규약이 공통인지 확인한 뒤 기존 적용 방식을 따른다. 컬럼마다 다르면 명시적 적용을 검토한다.
   - 기존 Converter가 미정의 값이나 예외를 null로 바꾼다는 이유로 그 동작을 새 매핑의 기본 취향으로 복제하지 않는다. 현재 계약을 확인하고 필요한 변경 범위 안에서 처리한다.
   - Converter 추가를 위해 DB 코드나 외부 API의 값 표현까지 함께 바꾸지 않는다. 요청에 포함된 변경만 수행한다.

## 결과물과 확인

- Entity 필드, 의미 있는 enum, 필요한 Converter가 실제 코드표와 맞아야 한다. DB 값을 뜻하는 자료형과 Java 필드의 변환 연결을 확인한다.
- 매핑을 추가·수정했다면 정의된 코드의 읽기·쓰기 왕복과 null·미정의 값의 의도한 처리를 검증한다. 공통 적용 범위를 바꿨다면 같은 Java 타입을 사용하는 필드도 확인한다.
- 코드표의 근거와 검증 범위를 보고한다. 소스에서만 확인한 코드 의미를 운영 데이터로 검증했다고 표현하지 않는다.
