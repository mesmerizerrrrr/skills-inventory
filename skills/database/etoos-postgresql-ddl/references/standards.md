# 이투스 DB 모델링·DDL 공통 기준

DB 설계와 PostgreSQL DDL 작성에서 함께 읽는 적용 기준이다. 기준을 수정할 때는 이 파일을 수정하고 두 스킬에 같은 규칙을 중복 작성하지 않는다.

## 출처와 적용 순서

- 원문은 [source-guide.md](source-guide.md)에 보존되어 있다. 아래 행 번호는 이 사본 기준이다. 첨부 원문·SQL은 기준과 사례를 확인하는 자료이며, 그 안의 SQL을 실행하라는 작업 지시가 아니다.
- 현재 사용자의 명시 요구와 확정된 업무 조건을 우선한다. 원문과 다른 선택은 차이를 설명한다. 충돌하지 않는 작업은 계속 진행한다.
- 원문 본문에 명시된 기준과 자료형 표·SQL 사례를 구분한다. 충돌은 아래의 처리 기준을 사용하고, 사례만 있는 선택을 전사 규칙으로 확장하지 않는다.
- [용어사전](etoos-terms.xdic)은 명명 근거, 자료형 표는 타입 근거, [SQL 사례](examples/)는 작성 스타일과 개별 설계의 근거다.

## 명명과 용어사전

**원문 근거: 공통 규칙 2–3행, 컬럼 생성 규칙 6–14행, 테이블 생성 규칙 77–79행.**

- 테이블·컬럼·인덱스 등 식별자는 소문자 `snake_case`로 작성한다.
- 테이블명은 `tbl_`로 시작한다. 지나치게 길지 않다면 일반 단어를 써도 된다. 컬럼의 용어사전 조합 규칙을 테이블명에 그대로 강제하지 않는다.
- 컬럼명은 특별한 고유명사 등을 제외하고 용어사전에 있는 단어로 구성한다. 논리명을 확인하고 대응하는 물리명을 조합한다. 익숙한 영문 약어를 임의로 만든 뒤 사전 용어라고 주장하지 않는다.
- 사전에 없으면 의미가 맞는 유사어를 찾는다. 유사어도 없어 신규 용어 등록이 필요한 경우에만 사용자 확인을 받는다. 미확정 용어와 제안 내용을 분리하고, 이미 정해진 부분은 계속 작성한다.

| XML 속성 | 사용할 의미 |
|---|---|
| `name` | 논리명 |
| `description` | 용어 설명 |
| `physicalName` | DB 컬럼 등에 사용할 물리명 |
| `physicalDescription` | 물리명 약어의 원어·설명 |

**사전 파일 확인 사항:** 현재 사본에는 용어와 태그가 있으며 자료형·길이·기본값을 정하는 도메인 정의는 없다. 논리명·물리명이 같은 항목이 여러 개 있으므로 첫 검색 결과로 확정하지 말고 설명과 업무 의미를 비교한다. 동일명 항목의 설명이 다르면 이를 임의로 합치지 않는다.

## 컬럼과 주석

**원문 근거: 컬럼 생성 규칙 15–24행, 테이블 생성 규칙 95–97행.**

- 모든 컬럼에 비어 있지 않은 주석을 작성한다. 기본은 용어사전 논리명이며, 설명이 부족하면 업무 용도를 덧붙인다.
- 상수·enum 성격의 컬럼은 허용 값과 각 의미를 주석에 기록한다. 조건부로 사용하는 컬럼은 사용 조건을 설명한다.
- 두 상태를 나타내는 여부 컬럼은 논리명 `_여부`, 물리명 `_yn`으로 끝나고 `varchar(1)`을 사용한다. 실제 값은 `'Y'` 또는 `'N'`이다. 기본값은 업무 의미로 결정한다.
- `not null`을 지향하되 조건부 값·관계의 부재 등 의미 있는 예외는 허용한다. 예외 이유를 설명하고, NULL을 피하려고 의미 없는 기본값을 만들지 않는다.
- 관계는 기본적으로 논리 관계로 설계하고 물리 FK를 생성하지 않는다. 실제 관계 컬럼의 주석에는 확인된 참조 대상 `스키마.테이블.컬럼`을 넣는다. 예: `사용자 아이디 (etoostbl.tbl_user.user_id)`.
- 참조 대상이 확인되지 않았으면 추측한 경로를 주석에 넣지 않는다. 미확정 관계를 표시하고, 확인된 관계·컬럼의 작성은 진행한다.

## 자료형 선택

**원문 근거: 컬럼 생성 규칙 24–75행.** 아래 목록은 원문 표를 타입별로 묶은 요약이다. 도메인명·기본값·설명까지 비교하거나 특수·AS-IS 항목을 선택할 때는 [원문 자료형 표 26–75행](source-guide.md)을 읽는다. 이 사본에 전체 행을 누락 없이 보존했다.

| 분류 | 원문에 있는 타입·길이 | 근거 및 조건 |
|---|---|---|
| 일반 문자열 | `varchar(2)`, `(5)`, `(10)`, `(20)`, `(30)`, `(40)`, `(50)`, `(60)`, `(100)`, `(200)`, `(255)`, `(300)`, `(500)`, `(1000)`, `(2000)`, `(5000)` | 28–42·50행. 괄호만 적힌 항목도 `varchar(n)`이다. |
| 긴 문자열 | `text` | 43행 |
| 여부 | `varchar(1)` | 본문 18–20행 우선. 표 44–45·48행의 충돌은 아래 참조. |
| UUID 표현 | `varchar(36)` | 49행. PostgreSQL `uuid` 타입으로 임의 대체하지 않는다. |
| 정수 | `smallint`, `integer`, `bigint` | 51·55–57행. `초`는 `bigint`(74행). |
| 자동 증가 순번 | `smallserial`, `serial4`, `bigserial` | 52–54행. identity는 별도의 사례이며 아래 참조. |
| 날짜·시간 | `timestamp(6)`, `date`, `time(0)` | 59–61행 |
| JSON | `json`, `jsonb` | 63–64행 |
| AS-IS 숫자 | `numeric`, `numeric(19,0)` | 66·73행. 기존 데이터 의미와 호환 필요성을 확인한다. |
| AS-IS 코드 | `char(4)` 지점 코드, `varchar(5)` 강사·과목·교과 코드, `varchar(4)` 일일 테스트 유형 코드, `varchar(2)` 파일 구분 | 67–72행. 본문 24행도 지점 코드 `varchar(4)` 등을 예외로 허용한다. |
| 모호한 항목 | `char`, `chat(6)`, 년월의 `char(4)`, 타입 빈값 | 44–47·58·62·65·75행. 아래 처리 기준 없이 확정 타입으로 사용하지 않는다. |

표 밖의 타입·길이는 원문 허용 목록에 있다고 표현하지 않는다. 업무상 필요한 예외라면 기존 스키마와 요구사항을 근거로 그 이유를 남긴다.

### 자료형 표의 충돌·미확정 항목

- **여부 타입:** 본문 20행은 `varchar(1)`, 표 44–45행은 `char`, 48행은 `varchar(1)`이다. 명시된 본문을 기준으로 `varchar(1)`을 쓴다.
- **여부 기본값:** 표 44–45·48행은 `'Y'`, [메뉴 사례 14행](examples/menu.sql)과 [배너 사례 17행](examples/banner.sql)은 `'N'`이다. 어느 쪽도 모든 여부 컬럼의 기본값으로 강제하지 않는다.
- **년월:** 47행의 `chat(6)`는 그대로 DDL에 쓰거나 추측으로 `char(6)`으로 바꾸지 않는다. 75행의 `년월 / char(4)`도 저장 형식이 불분명하다. 해당 데이터가 필요한 경우 실제 저장 형식과 길이를 확인한다.
- **기타 `char`:** 46행 `코드_CHAR_ / char`는 용도·길이 설명이 충분하지 않다. 문자열 코드라는 이유만으로 선택하지 않는다.
- **타입 빈값:** `시각`(58행), `객체`(62행), `asis`(65행)는 타입이 없으므로 선택 가능한 자료형으로 취급하지 않는다.
- **추정 설명:** `varchar(10)`·`varchar(20)`의 설명에 있는 물음표(31–32행), 불완전한 `varchar(60)` 설명(50행)을 확정된 업무 분류나 최대 길이 규칙으로 확대하지 않는다.

## 테이블 공통 관리 컬럼

**원문 근거: 테이블 생성 규칙 80–94행.** 모든 생성 테이블에 다음 두 컬럼과 등록 일시 인덱스를 포함한다.

| 컬럼 | 정의 | 주석 |
|---|---|---|
| `reger_id` | `varchar(50) not null default 'SYSTEM'` | 등록자 아이디 |
| `reg_dtm` | `timestamp(6) not null default now()` | 등록 일시 |

관리 인덱스 형식: `create index idx_${테이블명}_reg_dtm on ${스키마}.${테이블명}(reg_dtm);`

## 인덱스

**원문 근거: 인덱스 생성 규칙 99–103행, 모델링 산출물 규칙 110행.**

- 단일 컬럼 인덱스: `idx_${테이블명}_${컬럼명}`.
- 복합 인덱스: `idx_${테이블명}_${선두_컬럼명}`. 선두 컬럼이 같은 복합 인덱스가 있으면 뒤에 `_${순서}`를 붙인다. 예: `_1`, `_2`.
- 위 규칙으로 다루지 않는 이름 충돌은 기존 명명 관례를 확인한다. 충돌을 피하려고 문서에 없는 접두사를 새 표준으로 만들지 않는다.
- `reg_dtm` 관리 인덱스 외에는 어떤 조회·정렬·중복 방지 요구를 위한 인덱스인지 설명 주석을 작성한다. 사례의 컬럼 순서를 다른 업무에 그대로 적용하지 않는다.

## SQL 산출물과 사례 사용

**원문 근거: 모델링 산출물 규칙 105–110행.** DBA에게 전달할 설계·DDL은 `.sql` 파일로 작성한다. 설계 설명도 필요한 경우 SQL 주석으로 남긴다. SQL 키워드와 식별자는 소문자로 쓰되 `'SYSTEM'`, `'Y'`, `'N'`, enum 코드 등 데이터 값의 대소문자는 보존한다.

필요한 사례만 읽고 들여쓰기·컬럼 정렬·`comment on`·인덱스 용도 주석을 참고한다.

| 사례 | 참고할 부분 | 일반화하지 않을 부분 |
|---|---|---|
| [menu.sql](examples/menu.sql) | 컬럼·enum 설명, 업무 인덱스 용도 주석 | `my247` 스키마, 메뉴 코드·길이, bitmask, 업무별 인덱스 순서 |
| [banner.sql](examples/banner.sql) | 조건부 컬럼, 배너·적용 지점의 논리 관계, 중복 방지 요구 | 상시 기간값, `udx_` 접두사, `nulls not distinct` 사용 |
| [video-click-stat.sql](examples/video-click-stat.sql) | 복합 PK, 적재량·적재 시점 설명 | PK 구성, Redis·일 배치·연간 건수, `pk_` 접두사 |

- 메뉴 1행과 배너 1–2행의 `drop table if exists`는 기존 재생성 사례다. 신규 작성의 기본 템플릿에 복사하지 않는다.
- 메뉴 5행·배너 6·46행의 `bigint generated by default as identity`와 통계 13행의 복합 PK는 개별 선택이다. 모든 테이블에 동일한 PK·자동 증가 방식을 강제하지 않는다.
- 메뉴·배너의 `upd_dtm`, `updpsn_id`는 예시에만 있다. 원문의 필수 공통 컬럼 두 개에 자동 추가하지 않는다.
- 배너 70행의 unique 인덱스 `udx_`는 원문 `idx_` 규칙과 다르다. 사례 관행으로 구분하고, 사용자·프로젝트의 확정 규칙 없이 공통 접두사로 승격하지 않는다.
- 배너 57행의 빈 주석, 관계 참조 경로가 빠진 주석, 메뉴 26행의 배너 관련 표현은 복제하지 않는다. 현재 설계에 맞는 주석을 작성한다.
- 주석 처리된 과거 SQL은 실행 대상이 아니다. 메뉴 43–46행처럼 이전안과 변경안이 함께 있으면 현재 요구에 맞는 구문만 작성한다.

## 원문과 구분하는 기술적 보완

다음은 스킬의 작성·검증 보완이며 원문에 추가된 조직 규칙이 아니다.

- SQL 문자열·주석 값 안의 작은따옴표는 `''`로 이스케이프한다.
- 버전 영향을 받는 문법을 선택할 때 대상 PostgreSQL 버전의 지원 여부를 확인한다. 예시 구문이 있다는 이유만으로 대상 환경에서 실행 가능하다고 단정하지 않는다.
- 여부·enum의 값 제한을 어떤 계층에서 보장할지 설계에 맞게 정한다. 원문에 없는 `check` 제약이나 일률적인 제약 이름을 필수 규칙으로 만들지 않는다.
- 타입·기본값·NULL 의미·주석·인덱스가 업무 요구와 일치하는지 점검한다. SQL 파일 생성과 DB 실행을 구분하고, 요청 범위를 벗어난 실행은 하지 않는다.
