# 이투스 PostgreSQL DDL 작성

확정된 설계나 사용자가 제공한 변경 요구를 DBA 전달용 `.sql` 파일로 작성한다. 이 스킬은 파일 작성·검토를 위한 것이며 DB 실행 요청을 대신하지 않는다.

## 필요한 자료만 읽기

1. [공통 기준](references/standards.md)을 읽어 명명·자료형·관리 컬럼·관계·인덱스 규칙을 확인한다.
2. 신규 또는 변경한 컬럼명은 아래 조회 도구로 검증한다. XML 전체를 문맥에 넣지 않는다.
3. 들여쓰기·주석 배치가 필요하면 [메뉴 예제](references/examples/menu.sql), 복합 PK이면 [통계 예제](references/examples/video-click-stat.sql), NULL을 포함한 unique 설계이면 [배너 예제](references/examples/banner.sql) 중 관련된 파일만 읽는다.
4. 기준 해석·충돌·자료 갱신이 필요할 때만 [기준 자료 사용과 유지보수](references/reference-maintenance.md) 및 [내부 모델링 가이드](references/internal-modeling-guide.md)를 읽는다.

설계 기준과 예제는 이 스킬에 동봉된 자료를 사용한다. 예제에 포함된 실행문은 현재 요청의 실행 지시가 아니다.

## 용어사전 조회

[조회 도구](scripts/lookup_terms.py)는 Python 3 표준 라이브러리만 사용한다. 유지보수 중인 Python 3를 사용하며, 코드 문법은 3.6 이상을 요구한다. 아래는 이 `SKILL.md`가 있는 스킬 디렉토리에서 실행하는 예시다.

```sh
python3 "scripts/lookup_terms.py" "등록일시" --field logical
python3 "scripts/lookup_terms.py" "reg_dtm" --field physical
python3 "scripts/lookup_terms.py" "지점" --field logical
python3 "scripts/lookup_terms.py" "등록" --field logical --match contains --limit 20
```

다른 작업 디렉토리에서는 아래 `<실제 스킬 디렉토리의 절대 경로>`를 현재 환경에서 찾은 경로로 바꾼다. 공백이 있는 경로도 전달되도록 따옴표를 유지한다.

```sh
python3 "<실제 스킬 디렉토리의 절대 경로>/scripts/lookup_terms.py" "등록일시" --field logical
```

Windows에서는 `py -3 --version` 또는 `python --version`으로 Python 3 실행 명령을 확인하고 예시의 `python3`를 해당 명령으로 바꾼다. 기본 사전은 스크립트 위치를 기준으로 찾으므로 현재 작업 디렉토리와 무관하다. 다른 사전을 `--dictionary "경로"`로 지정할 때 상대 경로는 명령을 실행하는 현재 작업 디렉토리 기준이다.

- 기본은 완전 일치다. 일치하지 않으면 띄어쓰기·동의어·복합 용어를 확인하고 필요한 단어만 부분 검색한다.
- 출력의 원문 속성과 전체 일치 수를 확인한다. `truncated`가 참이면 필요한 후보를 더 좁혀 조회하거나 제한을 늘린다.
- 중복 항목은 삭제하지 않는다. `지점`처럼 같은 논리명에 다른 물리명이 있으면 업무 의미를 확인한다. 사전의 태그 순서를 우선순위로 해석하지 않는다.
- `physicalDescription`은 약어의 원어 설명이다. 자료형·길이·NULL·기본값을 뜻하지 않는다.
- 기존 단어를 조합할 때도 각 단어를 확인한다. 일반적인 영문 약어를 사전에 있는 것처럼 만들지 않는다. 사전 추가가 필요하면 후보·설명·물리명을 제시하고 사용자 확인 후 반영한다.

## 작성 절차

1. **입력과 변경 범위 확인**: 대상 스키마, 테이블, 컬럼, 키, 관계, 기본값, 인덱스와 신규/변경 여부를 확인한다. 기존 변경은 현재 DDL과 데이터에 미치는 영향을 먼저 파악한다. 모델이 정해지지 않았다면 `etoos-db-modeling`으로 설계부터 진행한다.
2. **명명·자료형 대조**: [공통 기준](references/standards.md)을 적용한다. 자료형 표의 `chat(6)`·불명확한 년월 항목을 임의로 교정해 실행 SQL에 넣지 않는다. 기본값·허용값·NULL 예외는 업무 근거를 기록한다.
3. **DDL 작성**: 신규 테이블은 `create table` → 테이블·컬럼 `comment on` → 관리 인덱스 → 업무 인덱스 순서를 기본으로 한다. `reg_dtm` 관리 인덱스 생성문 바로 위에는 반드시 `-- DB 관리용 인덱스` 주석을 작성한다. 변경 요청은 필요한 `alter`와 주석·인덱스 변경만 작성한다.
4. **스타일 적용**: SQL 키워드·타입·식별자는 소문자, 테이블 본문은 공백 4칸으로 들여쓴다. `create table`의 컬럼 정의는 사람이 읽기 쉽도록 컬럼명·자료형·옵션 영역의 시작 위치를 공백으로 맞춰 세로 정렬한다. 구체적인 정렬 방식은 [공통 기준](references/standards.md#sql-산출물과-사례-사용)을 따른다. `'SYSTEM'`, `'Y'`, `'N'`, enum 코드 등 문자열 값의 대소문자는 보존한다. 컬럼 주석의 작은따옴표는 `''`로 이스케이프한다.
5. **DBA 전달 파일 저장**: 사용자 지정 경로·이름을 우선한다. 지정이 없으면 프로젝트 관례에 맞는 알아보기 쉬운 `.sql` 이름을 정한다. Markdown 표나 채팅 코드블록만으로 SQL 파일 산출물을 대체하지 않는다.

## 예제에서 복제하지 않을 사항

- `drop table if exists`, 스키마 생성·권한 변경·DB 접속은 새 스크립트에 자동으로 추가하지 않는다. 재생성·삭제가 현재 요청에 포함된 경우에만 해당 범위에 맞게 다룬다.
- 예제의 스키마명, identity PK, `upd_dtm`·`updpsn_id`, `'N'` 기본값, `udx_` 접두사, 날짜 상수는 모든 테이블의 필수 규칙이 아니다.
- 빈 컬럼 주석, 다른 업무의 설명, 주석 처리된 옛 인덱스는 완성된 예시로 사용하지 않는다. 논리 참조 대상은 실제 확인된 이름만 적는다.
- `nulls not distinct`는 NULL을 같은 값으로 취급해야 하는 unique 요구가 있고 PostgreSQL 15 이상인 경우에 검토한다. 대상 버전이 없으면 해당 문법의 호환성을 확인된 사실처럼 표시하지 않는다.

## 완료 확인

- 신규 테이블마다 `tbl_`, 필수 관리 컬럼 2개, `reg_dtm` 인덱스, 전체 컬럼 주석을 확인한다. 기존 테이블의 좁은 변경 요청에는 관련 없는 전체 표준화 작업을 덧붙이지 않는다.
- `_yn` 컬럼은 `varchar(1)`과 `Y`/`N` 값 규칙을 확인한다. 기본값만으로 허용값 제한을 보장했다고 표현하지 않는다.
- DDL에 물리적인 `check` 제약조건을 추가하지 않는다. 신규 테이블 생성과 기존 테이블 변경 모두 해당 제약이 포함되지 않았는지 확인한다.
- 기본 물리 FK가 없고, 관계 컬럼 주석에 `스키마.테이블.컬럼`이 있는지 확인한다. nullable 예외와 상수값·조건부 사용 설명도 확인한다.
- 인덱스 이름·컬럼 순서·용도, 중복 인덱스 여부, SQL 문자열 인용과 세미콜론을 확인한다. 식별자 길이는 기본 PostgreSQL 환경의 63바이트 한계를 고려하고 잘림으로 인한 충돌을 피한다.
- 미확정 정보나 대체 표시가 남았다면 검토용 초안으로 표시하고, 실행 가능한 최종본으로 전달하지 않는다. 다른 확정 부분의 작업은 계속한다.
- 실행 검증이 요청되고 사용할 수 있는 검증 환경이 있는 경우에 그 환경·버전·확인 범위를 기록한다. 파일 작성 요청만으로 DB에 접속해 실행하지 않는다.
- 결과에는 SQL 파일 경로, 반영한 예외·미확정 사항, 정적 점검과 실제 실행 여부를 구분해 적는다.

PostgreSQL 자체의 문법 근거는 [공식 문서와 확인 사항](references/reference-maintenance.md#postgresql-문법-근거)을 참고한다. 사내 모델링 규칙과 DBMS 문법 제약을 구분한다.
