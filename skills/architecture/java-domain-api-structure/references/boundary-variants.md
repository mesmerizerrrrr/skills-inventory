# 진입점과 후처리 경계

앱/내부 호출을 함께 구현하거나 기존 업무에 후처리를 추가할 때 필요한 절만 읽는다.

## App/Internal 진입점

- 같은 도메인 안에 `<Domain>Controller`와 `Internal<Domain>Controller`를 둔다. 앱 경로 `/api/v1/...`, 내부 경로 `${api-path.internal}/...`처럼 진입점을 구분할 수 있으며 실제 경로는 대상 프로젝트의 설정을 따른다.
- 요청자와 대상자를 구별한다. 예를 들어 앱은 인증 주체의 학생 코드를, 내부 호출은 권한 확인을 거친 요청의 대상 학생 코드를 같은 서비스에 전달할 수 있다. 이 입력 차이는 Controller 또는 내부용 요청 DTO에 두고 업무 구현을 복제하지 않는다.
- 경로 분리만으로 권한이 보장된다고 가정하지 않는다. 대상 프로젝트에서 해당 경로를 처리하는 인증·권한 설정과 요청자 전달 방식을 함께 확인한다. Swagger용 부모 클래스나 어노테이션을 인증 구현으로 간주하지 않는다.
- 응답 범위가 다르면 서비스의 조회 메서드·DTO를 구분할 수 있다. 두 진입점의 서명과 응답을 무조건 같게 만들지는 않는다.
- 내부 API가 필요한 기능에만 추가한다. 모든 앱 API에 내부 쌍을 만들거나 현재 호출 요구가 없는 Internal Controller를 추가하지 않는다.

## 이벤트 후처리

업무 서비스가 발생 사실을 발행하고, 알림 예약·파일 정리 등 별도 책임의 서비스가 필요한 후처리를 맡게 한다.

- 이벤트는 소유 도메인의 `application/event`에 두고, `ScheduleChangedEvent`, `MeasurementStoppedEvent`, `FileRemoveEvent`처럼 이름에 발생 사실이나 처리 의도를 드러낸다. 불변 값 묶음에는 record를 사용할 수 있다.
- 이벤트에는 식별자와 수신 처리에 필요한 값을 담는다. 변경된 데이터를 다시 조회할 때는 식별자를, 발생 시점의 정보가 필요할 때는 해당 시각·대상 정보도 전달한다. 무조건 ID 하나만 허용하는 규칙은 아니다.
- 알림 예약, 자동 측정 예약, 파일 정리는 목적별 서비스에서 받는다. 새 후처리를 추가할 때 기존 발행자를 재사용할 수 있는지 먼저 확인한다.
- DB 변경 성공 뒤에 수행해야 하는 후처리는 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`을 검토하고, 비동기 실행이 필요한 경우 `@Async`를 함께 사용한다. 즉시 수신이 필요한 처리는 `@EventListener`를 사용할 수 있다. 기존 이벤트의 발행 트랜잭션·실행 시점·실패 전달 방식을 확인하고 맞추며 모든 이벤트를 비동기 또는 후커밋으로 일괄 변경하지 않는다.
- 같은 요청에서 결과가 필요한 처리나 함께 성공해야 하는 변경을 이 관례만을 이유로 이벤트로 옮기지 않는다. 이 패턴 자체가 재시도·전달 보장을 제공한다는 약속도 하지 않는다.

후처리를 바꾸었으면 발행 → 수신 연결, 기존 호출자의 트랜잭션 유무, 필요한 조회 범위가 맞는지 해당 흐름에서 확인한다. 업무별 시간표·Redis 키·반복 일정 정책은 이 스킬의 공통 규칙이 아니다.
