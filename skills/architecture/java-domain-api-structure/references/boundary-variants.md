# 진입점과 후처리 경계

앱/내부 호출을 함께 구현하거나 기존 업무에 후처리를 추가할 때 필요한 절만 읽는다.

## App/Internal 진입점

- 같은 도메인 안에 `<Domain>Controller`와 `Internal<Domain>Controller`를 둔다. 원본 프로젝트의 앱 경로는 `/api/v1/...`, 내부 경로는 `${api-path.internal}/...`이다. 다른 프로젝트에는 그 프로젝트의 경로 설정을 쓴다.
- 요청자와 대상자를 구별한다. 원본 플랜카드 생성에서 앱은 인증 주체의 학생 코드를, 내부 호출은 내부 요청의 학생 코드를 같은 서비스에 전달한다. 이 입력 차이는 Controller 또는 내부용 요청 DTO에 두고 업무 구현을 복제하지 않는다.
- 경로 분리만으로 권한이 보장된다고 가정하지 않는다. 대상 프로젝트에서 해당 경로를 처리하는 인증·권한 설정과 요청자 전달 방식을 함께 확인한다. 원본의 Swagger용 부모 클래스 이름을 인증 구현으로 복사하지 않는다.
- 응답 범위가 다르면 서비스의 조회 메서드·DTO를 구분할 수 있다. 두 진입점의 서명과 응답을 무조건 같게 만들지는 않는다.
- 내부 API가 필요한 기능에만 추가한다. 모든 앱 API에 내부 쌍을 만들거나, 과거에 삭제된 Internal Controller를 재생성할 근거로 사용하지 않는다.

## 이벤트 후처리

보존할 선택은 업무 서비스가 알림 예약·파일 정리 구현을 직접 끌어안지 않고, 발생 사실을 발행하고 해당 책임의 서비스가 처리하게 한 방식이다.

- 이벤트는 소유 도메인의 `application/event`에 두고, 이름에 발생 사실이나 처리 의도를 드러낸다. 원본은 `PlanCardEntityUpsertEvent`, `PlanCardRecordStopEvent`, `FileRemoveEvent`와 같은 record를 사용한다.
- 이벤트에는 식별자와 수신 처리에 필요한 값을 담는다. 원본 플랜카드 변경 이벤트는 번호를 전달하고 수신자가 다시 조회하며, 측정 이벤트는 시각·학생 정보도 전달한다. 무조건 ID 하나만 허용하는 규칙은 아니다.
- 알림 예약은 `PlanCardReserveNotificationService`, 자동 측정 예약은 `PlanCardReserveRecordService`, 파일 정리는 `FileEventService`처럼 목적별 서비스에서 받는다. 새 후처리를 추가할 때 기존 발행자를 재사용할 수 있는지 먼저 확인한다.
- DB 변경 성공 뒤에 수행하는 기존 후처리는 `@TransactionalEventListener(AFTER_COMMIT)`와 `@Async`를 사용한다. 원본에는 `@EventListener`로 받는 측정 시작 알림 정리도 있으므로, 기존 이벤트의 발행 트랜잭션·실행 시점·실패 전달 방식을 확인하고 맞춘다. 모든 이벤트를 비동기 또는 후커밋으로 일괄 변경하지 않는다.
- 같은 요청에서 결과가 필요한 처리나 함께 성공해야 하는 변경을 이 관례만을 이유로 이벤트로 옮기지 않는다. 이 패턴 자체가 재시도·전달 보장을 제공한다는 약속도 하지 않는다.

후처리를 바꾸었으면 발행 → 수신 연결, 기존 호출자의 트랜잭션 유무, 필요한 조회 범위가 맞는지 해당 흐름에서 확인한다. 업무별 시간표·Redis 키·반복 일정 정책은 이 스킬의 공통 규칙이 아니다.
