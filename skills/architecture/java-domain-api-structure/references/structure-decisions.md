# 구조 선택과 적용 조건

기본 패키지 배치와 다른 코드가 있거나 새 계층의 필요성을 판단할 때 사용한다. 기존 구조를 이름만 맞추어 옮기기보다 기능의 소유권과 호출 경계를 먼저 확인한다.

## 계층을 나누는 기준

| 상황 | 선택과 이유 | 적용 경계 |
| --- | --- | --- |
| Controller가 호출하는 주 업무 서비스 | 서비스 인터페이스와 `impl` 구현을 구분하여 진입점이 업무 계약을 호출하게 한다. | 이벤트 수신·예약 실행·외부 처리만 맡는 전담 서비스까지 인터페이스를 만들 필요는 없다. |
| JPA 기본 기능과 복합 조회가 함께 필요 | `Repository`가 `JpaRepository`와 `CustomRepository`를 결합하고, 별도 조회 구현은 `infrastructure/impl`에 둔다. | 파생 쿼리만 필요한 저장소에 빈 CustomRepository를 추가하지 않는다. |
| 앱과 내부 호출에서 같은 업무를 실행 | 각 Controller가 요청자·대상자와 입력을 정리하고 같은 서비스를 호출한다. | 응답 범위가 다르면 별도 조회 메서드나 DTO를 사용할 수 있다. 내부 호출 요구가 없는 API에는 쌍을 만들지 않는다. |
| 알림 예약·파일 정리 등 별도 책임의 후처리 | 업무 서비스가 이벤트를 발행하고 책임별 서비스가 수신하여 변경 이유를 분리한다. | 같은 요청에서 필요한 결과나 함께 성공해야 하는 변경을 무조건 이벤트로 옮기지 않는다. 실행 시점은 [진입점과 후처리 경계](boundary-variants.md)를 따른다. |

## 기존 변형을 유지하는 경우

- `domain`의 위치, `presentation` 아래 기능별 하위 폴더, DTO의 request/response 구분 유무는 대상 도메인의 배치를 따른다. 기본 디렉터리 예시와 다르다는 이유만으로 파일을 옮기지 않는다.
- 서비스가 `presentation.dto`를 사용하거나 Entity가 요청 DTO를 직접 받는 구조라면 해당 계약을 확인하고 이어 쓸 수 있다. 이 스킬은 별도 port/adapter 또는 command 계층의 도입을 요구하지 않는다.
- 여러 진입점이 있다는 사실만으로 Facade 계층을 만들지는 않는다. 기존 서비스 조합만으로 책임을 표현할 수 있는지 먼저 판단한다.
- 순환 의존이 생기면 서로 어떤 책임을 호출하는지 확인한다. 불필요한 주입 제거, 책임 분리, 별도 후처리 분리 중 실제 원인을 해결하는 방법을 고르며 파일 이름이나 패키지만 바꾸어 해결했다고 판단하지 않는다.

## 구현에서 확인할 연결

예를 들어 앱이 본인의 일정 생성을, 내부 API가 권한 있는 관리자의 대상자 일정 생성을 제공한다면 두 Controller는 대상자 결정과 권한 확인을 맡고 일정 생성 서비스는 공유한다. 서비스가 생성 완료 이벤트를 발행해 알림을 예약하는 경우, 알림 서비스는 이벤트에 실린 식별자로 데이터를 조회하거나 발생 시점의 값을 사용한다. 어느 쪽이 맞는지는 후처리에 필요한 데이터의 시점과 범위로 정한다.

변경 후에는 Controller → Service → Repository의 실제 연결과 이벤트 발행 → 수신 연결을 확인한다. 패키지 형태가 맞는 것만으로 인증·트랜잭션·후처리 성공까지 확인된 것은 아니다.

## 트랜잭션 호출 경계

Service의 `readOnly`를 정할 때 상위 Service 호출, 같은 객체 내부 호출 또는 읽기·쓰기 전환이 있으면 확인한다.

- 기본 프록시 방식에서 같은 객체 내부의 메서드 호출은 별도 트랜잭션 어드바이스를 통과하지 않는다. 내부 쓰기 메서드에 `@Transactional`을 붙였다는 이유로 외부의 읽기 전용 트랜잭션이 쓰기로 전환된다고 판단하지 않는다.
- 기본 전파 방식인 `REQUIRED`로 기존 트랜잭션에 참여하면 상위 트랜잭션의 특성을 따른다. 읽기 전용 상위 흐름에서 쓰기 메서드를 호출해야 한다면 실제 쓰기를 포함한 진입 경계를 `false`로 구성한다. 반대로 쓰기 트랜잭션 안의 조회는 내부 메서드가 `true`여도 별도 읽기 전용 DB로 분기된다고 보장하지 않는다.
- 라우팅만 바꾸려고 `REQUIRES_NEW`를 일괄 추가하지 않는다. 먼저 하나의 업무가 함께 성공·실패해야 하는 범위와 기존 호출 구조를 확인한다. 독립 트랜잭션이 실제 요구일 때만 별도 경계를 선택한다.
- 읽기 전용 DB 분기는 프로젝트의 데이터소스 라우팅 구현이다. 트랜잭션 상태를 확인하는 시점과 실제 커넥션을 획득하는 시점을 함께 확인한다. 어노테이션 선언의 정적 확인과 라우팅 환경에서의 실제 DB 선택 확인을 구분한다.

Spring 동작 근거는 [어노테이션 적용과 프록시 호출](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [기존 트랜잭션 참여](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html), [readOnly의 의미](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Transactional.html#readOnly())를 참조한다. 조회에는 `readOnly = true`를 명시하고 쓰기에는 `@Transactional`의 기본값 `false`를 사용하며, 유효한 값을 DB 분기 기준으로 삼는 것이 이 인벤토리의 작성 관례다. 모든 Spring 애플리케이션에 자동으로 존재하는 라우팅 기능은 아니다.
