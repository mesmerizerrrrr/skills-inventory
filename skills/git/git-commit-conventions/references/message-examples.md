# 메시지 작성 예시

번호·업무명·코드는 형식을 설명하기 위한 가상 예시다. 실제 메시지에는 현재 변경 내용과 확인된 티켓 정보를 사용한다.

## 티켓이 있는 제목

| 확인된 입력 | 작성할 제목 |
| --- | --- |
| 번호 `PROJ-123`, 제목 `중복 예약 후 시간 목록 갱신 오류 수정` | `fix: [PROJ-123] 중복 예약 후 시간 목록 갱신 오류 수정` |
| 번호 `1234`, 제목 `[APP] 프로필 저장 오류 수정` | `fix: [1234] [APP] 프로필 저장 오류 수정` |
| 제공된 제목이 `[1234][APP] 프로필 저장 오류 수정` | `fix: [1234][APP] 프로필 저장 오류 수정` |

`[APP]`는 제목에 포함된 표시이므로 보존한다. 제목 전체를 다시 감싸 `fix: [1234][[APP] 프로필 저장 오류 수정]`으로 만들지 않는다. Jira 키와 숫자 번호를 서로 변환하지 않는다.

번호만 알고 제목을 모르면 원문 제목을 확인한다. 확인 전 초안이 필요하면 미확정임을 밝히고 `<원문 티켓명>`처럼 표시한다. 실제 커밋 메시지에 미확정 표시를 그대로 확정하지 않는다. 티켓이 없는 작업에는 번호나 티켓명을 새로 만들지 않는다.

## 변경 목적에 따른 타입

| 변경 | 타입과 판단 이유 |
| --- | --- |
| 새로운 검색 API 추가 | `feat`: 사용할 수 있는 기능이 늘어남 |
| 중복 예약 실패 후 시간 목록이 갱신되지 않는 오류 수정 | `fix`: 기존 기능의 잘못된 동작을 바로잡음 |
| 동일한 응답 타입 정의를 공통 파일로 이동 | `refactor`: 기능 의도를 유지하면서 중복과 구조를 정리함 |
| Java의 `@Schema` 설명만 수정 | `docs`: 소스 파일에 있어도 변경 목적은 문서 설명임 |
| 개발·운영 환경의 캐시 저장소 설정 분리 | `config`: 실행 환경을 구성하는 설정을 변경함 |
| 장애 재현을 위한 임시 진단 로그 추가 | `test`: 진단을 목적으로 함. 자동 테스트 추가나 성공을 뜻하지 않음 |

구조 정리 중 실제 오류 수정이나 응답 계약 변경도 포함했다면 그 목적을 메시지에 드러낸다. 변경을 구분할 수 있으면 커밋 분리를 검토하고, 분리하기 어려우면 주된 목적과 영향 범위를 설명한다. 파일 이동이나 이름 변경만 보고 전체 변경을 `refactor`로 판단하지 않는다.

## 제목만으로 충분한 변경

```text
docs: 상품 응답의 가격 필드 설명 수정
```

단순 변경에는 원인·해결책·영향도 본문을 형식적으로 덧붙이지 않는다.

## 티켓 제목과 실제 변경을 함께 설명

```text
fix: [PROJ-123] 중복 예약 후 시간 목록 갱신 오류 수정

- 예약 충돌 안내 확인 후 예약 창 닫기
- 선택한 날짜의 활성 시간 목록 재조회
```

티켓이 여러 저장소의 작업을 포함해도 본문은 현재 커밋의 변경만 설명한다. 서버에서 행 매핑만 수정했다면 다음과 같이 작성한다.

```text
fix: [PROJ-123] 중복 예약 후 시간 목록 갱신 오류 수정

- 예약 조회 결과의 열과 응답 필드 매핑 수정
```

현재 커밋에 없는 화면 재조회까지 완료했다고 쓰지 않는다.

## 복잡한 이슈의 선택적 본문

```text
fix: [PROJ-456] 예약 종료 시각 계산 오류 수정

- 원인 : 자정을 넘는 예약의 종료일을 시작일과 동일하게 계산
- 해결책 : 종료 시각이 시작 시각보다 이르면 다음 날로 계산
- 영향도 : 날짜를 넘는 예약의 종료 시각 표시
```

원인과 영향 범위가 확인됐을 때만 이 구성을 사용한다. 아직 확인되지 않은 원인이나 영향도를 채우기 위해 추측하지 않는다.

## 호환성을 깨는 변경

```text
feat(api)!: 상품 조회를 v2 API로 통합

BREAKING CHANGE: GET /v1/items를 제거하여 호출자는 GET /v2/items로 전환 필요
```

티켓 제목을 그대로 유지해야 한다면 꼬리말로 계약 변경을 명시할 수 있다.

```text
feat: [PROJ-789] 상품 조회 API 통합

- 기존 조회 경로 제거

BREAKING CHANGE: GET /v1/items를 제거하여 호출자는 GET /v2/items로 전환 필요
```

호환성 변경은 특정 타입에만 한정되지 않는다. 변경 목적에 맞는 타입을 선택하고 깨지는 계약과 필요한 대응을 설명한다.

## 내용과 검증 범위를 맞추기

| 확인된 변경 | 피할 설명 | 적절한 설명 |
| --- | --- | --- |
| DTO의 입력 길이 검증과 Entity 매핑 수정 | 운영 DB 컬럼 변경 완료 | 입력 길이 검증과 컬럼 매핑 변경 |
| 확인용 로그 추가 | 테스트 통과 | 오류 재현 확인용 로그 추가 |
| 배포 설정 파일 수정 | 운영 배포 완료 | 운영 배포 설정 수정 |

규칙을 수정할 때도 제목 형식, 티켓 원문 보존, 실제 변경 범위, 호환성 표시를 함께 확인한다. 예시의 특정 기능이나 숫자를 모든 작업의 규칙으로 확장하지 않는다.
