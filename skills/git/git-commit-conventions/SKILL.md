# Git 커밋 메시지 관례

## 적용 기준

이 문서의 제목·타입·티켓·본문 규칙으로 한글 커밋 메시지를 작성한다. 사용자 요청과 현재 작업 대상 저장소의 명시적 커밋 규칙을 우선한다. 메시지 추천 요청 자체가 커밋·push·기존 이력 수정 요청을 뜻하지는 않는다.

## 메시지를 만들기 전에

- 현재 요청에 포함된 변경 범위를 확인한다. 메시지 추천에 필요한 diff나 구체적인 변경 설명이 제공됐다면 그 자료를 사용한다. 저장소를 직접 조사하거나 실제 커밋을 수행할 때 staged 변경이 대상이면 `git diff --cached`를 기준으로 하고, 작업 트리 전체가 대상이면 unstaged 변경과 필요한 untracked 파일도 확인한다. 서로 다른 범위의 변경을 한 메시지에 섞지 않는다.
- 변경의 목적을 기준으로 타입을 고른다. 파일 확장자나 과거에 붙였던 타입만으로 결정하지 않는다. 같은 티켓을 여러 저장소에서 처리했더라도 본문에는 현재 저장소의 변경만 적는다.
- 티켓 번호와 제목은 사용자 제공 정보나 확인된 작업 맥락에서 가져온다. 번호만 있고 제목을 알 수 없다면 제목을 확인한다. 번호·제목을 추측하거나 단순 업무 요약을 원문 티켓명처럼 제시하지 않는다.

## 제목

티켓이 없을 때:

```text
<타입>: <변경 요약>
```

티켓이 있을 때:

```text
<타입>: [<티켓번호>] <티켓명>
```

- 소문자 타입 뒤에 `:`와 공백 한 칸을 둔다. 티켓 번호는 `PROJ-123` 같은 Jira 키와 `1234` 같은 숫자 모두 원문 그대로 쓴다.
- 티켓명에 포함된 `[APP]`, `[ADMIN]`, `[API]` 등의 표시는 유지한다. 티켓명 전체를 새 대괄호로 감싸지 않는다. 기존 제목이 `[1234][APP] ...`처럼 대괄호를 붙여 썼다면 그 배치도 유지할 수 있다.
- 티켓 없는 요약은 **업무 대상·조건 + 변경 내용**을 짧은 한글 명사형으로 쓴다. `추가`, `수정`, `변경`, `제거`, `분리`, `공통화`, `반영`처럼 실제 작업을 드러내는 표현으로 끝낸다. 코드 식별자와 API·DTO·swagger 같은 실무 용어는 필요한 경우 그대로 쓴다.
- 제목 끝 마침표, 이모지, 불필요한 존댓말은 기본적으로 쓰지 않는다. 티켓 원문 제목의 문장부호는 임의로 정리하지 않는다. `수정`, `커밋 누락 파일`만 적기보다 변경 대상을 드러낸다.
- 일반적인 기본형에는 `(scope)`를 붙이지 않는다. 프로젝트에서 요구하거나 구분에 도움이 되면 `fix(auth): 인증 오류 수정`처럼 영향 영역을 괄호로 표시할 수 있다. 고정 길이 제한은 대상 저장소가 정한 경우에 적용한다.

예시:

```text
feat: 상품 검색 API 추가
fix: 비활성 사용자의 알림 목록 조회 오류 수정
config: 개발 환경 캐시 저장소 분리 설정
fix: [PROJ-123] 중복 예약 후 시간 목록 갱신 오류 수정
fix: [1234][APP] 프로필 저장 오류 수정
```

## 타입 선택

| 타입 | 기본 용도 |
| --- | --- |
| `feat` | 신규 기능·API·화면·업무 기능 추가 |
| `fix` | 잘못된 동작, 누락된 처리, 예외·오류 수정 |
| `refactor` | 기능 의도를 유지하는 구조·명칭·중복 정리 |
| `docs` | 문서, JavaDoc, swagger 설명·예시, 설정 파일의 주석 변경 |
| `config` | 환경·profile·빌드·배포·CI/CD 설정 변경 |
| `test` | 테스트 코드 또는 테스트·진단 목적의 변경. 확인용 임시 로그를 포함할 수 있음 |

- 설정 관련 변경은 이 관례에서 `config`를 기본으로 검토한다. 모든 유지보수 변경을 `config`로 분류하지는 않는다. 저장소가 `build`·`ci` 등 별도 분류를 명시하면 해당 규칙을 따른다.
- `chore`, `perf`, `style`, `build`, `ci`, `revert` 등은 현재 변경이나 프로젝트 규칙상 필요할 때 사용한다.
- `refactor`는 기능 의도를 유지하는 구조 정리에 사용한다. 오류 수정과 기능 추가를 단순 정리로 표현하지 않는다. `test`라는 제목만으로 자동 테스트 추가나 테스트 통과를 주장하지 않는다.
- 기능 제거·계약 변경은 현재 목적과 프로젝트 규칙에 맞는 타입을 고른다. 제거라는 이유만으로 `refactor`로 고정하지 않으며, 호환성을 깨면 타입과 별개로 아래 breaking 표기를 적용한다.

## 본문

제목만으로 충분하면 본문을 생략한다. 이유·변경 항목·적용 조건이 필요하면 제목 다음 빈 줄을 두고 `- ` 목록으로 적는다.

```text
feat: 알림 목록 페이지 추가

- 알림 목록과 상세 내용 조회
- 열람한 알림을 읽음 상태로 변경
```

복잡한 이슈는 확인된 사실이 있을 때 `- 원인 :`, `- 해결책 :`, `- 영향도 :`로 정리할 수 있다. 모든 커밋에 이 세 항목을 요구하거나 빈 항목을 채우지 않는다. 실제 diff에 없는 다른 저장소의 수정, DB 반영·배포 완료·운영 검증·테스트 성공을 본문에 넣지 않는다.

## 형식과 호환성 변경

이 스킬은 Conventional Commits 1.0.0 형식을 사용한다. 제목은 `타입(선택적 scope)!: 설명`의 구성에서 scope와 `!`를 필요할 때만 넣는다. `feat`·`fix` 외 타입도 사용할 수 있으며, `config`, 한글 명사형, 티켓 배치는 이 스킬에서 정한 작성 규칙이다.

호환성을 깨는 변경이면 `!` 또는 대문자 `BREAKING CHANGE:`로 표시한다. `!`는 `feat(api)!: ...`처럼 콜론 바로 앞에 둔다. 티켓 제목을 유지하면서 단절적 변경을 설명해야 하면 빈 줄로 구분한 `BREAKING CHANGE: <깨지는 계약과 필요한 대응>` 꼬리말을 사용할 수 있다. `!`만 사용한다면 제목에서 깨지는 계약이 드러나야 한다.

Git 자동 merge/revert 제목, 빈 `fix:`, 콜론 뒤 공백 누락은 일반 작성 예시로 삼지 않는다. 새 메시지를 현재 변경과 대조해 내용과 형식을 확인한다. 적용에 필요한 규칙은 이 문서에 포함되어 있으며, [표준 원문](https://www.conventionalcommits.org/ko/v1.0.0/)은 선택적으로 확인할 수 있다.

## 결과 확인

- 제목의 타입·요약과 본문이 실제 커밋 대상 변경을 설명하는지 확인한다.
- 티켓이 있으면 번호와 원문 제목을 확인하고, 티켓이 없으면 불필요한 대괄호·가짜 번호를 넣지 않는다.
- 메시지 추천 요청에는 바로 복사할 수 있는 `text` 코드 블록을 제공한다. 실제 커밋 요청은 기존에 승인된 범위에서 수행하고, 메시지 작성과 커밋 완료를 구분해 알린다.
- 티켓 표기, 타입 선택, 본문의 설명 범위를 판단하기 어려울 때만 [메시지 작성 예시](references/message-examples.md)를 읽는다.
